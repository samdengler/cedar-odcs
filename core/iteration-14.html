Cedar authorization for MCP tools, iteration 14: the command line

The mechanism at the command line, for a colleague who has cloned the repository and wants to see it work on the existing use cases in minutes, and on their own domain soon after. Nine verbs, matching the official cedar command where the meaning is the same, and two ideas Cedar has no word for.

1. The problem

Thirteen iterations and two use cases are a lot to read before running anything. A colleague evaluating the approach against a third domain needs to see a decision within minutes of cloning, needs to ask a question the corpus never asked without writing a test, and needs to take the same question to Cedar's own playground when the answer surprises them. The unit tests do all of this and are unfriendly about it: they say pass or fail, and they say it in Python.

Cedar has a command line of its own, and a playground with shareable links. This iteration puts the mechanism behind verbs that match Cedar's where the meaning is the same, so a learner who knows one tool is not learning two vocabularies, and links every question to the playground.

2. Scope of this iteration

Built: the cedar-osdc command, installed by uv sync at the repository root, with nine verbs: run-tests, authorize, dry-run, check-access, share, build, validate, prove, and a placeholder new. Every verb runs against the orders and reservations use cases as they are; no new content was needed. The playground link was checked in a browser against the site's own decoder. Nine tests drive the commands.

Not built: the learning path and the guide (iteration 15), scaffolding a use case and building from a plain fields file (iteration 16), and any output format other than words.

The files are Cedar's own formats throughout: policies.cedar, entities.json, a .cedarschema, and the corpus in the integration-test form. A use case directory is the unit every command takes, the same directory the tests and the proofs use.

4. One call, run dry

A dry run is a tool call performed without its effect. The command builds the Gateway event iteration 10 documented, from a caller file of claims and the tool's arguments, and puts it through the request handler; with a response payload it runs the response leg too. The output is the decision in words:

$ cedar-osdc dry-run usecases/reservations --caller agent.json \
    --tool reservations___get_reservation \
    --arg recordLocator=ABC123 --arg lastName=Smith --response record.json
Caller     Agent::"reservations-assistant", customer-conversation
Tool       reservations___get_reservation  {"recordLocator": "ABC123", "lastName": "Smith"}
Request    forwarded: the verb round passed
Response   row 0 stripped: passengers[].passportNumber, passengers[].specialServiceRequests, remarks
Returned   {
             "recordLocator": "ABC123",
             ...

A rejected call says which verb was refused or which paths were, and exits nonzero. The caller file is the same JSON of claims the fixtures use, so the three token shapes from iteration 13 are ready to hand.

5. What a token grants

The corpus states expected decisions and run-tests holds the policies to them. check-access states nothing in advance: for one token it asks every verb the schema declares, every path in the classification map, and every path in the writers map, and reports the answers. The presented pair and a record to decide on are options:

$ cedar-osdc check-access usecases/reservations --caller agent.json \
    --presented locator=ABC123 --presented lastName=Smith
Access of Agent::"reservations-assistant" (customer-conversation), presenting {"locator": "ABC123", "lastName": "SMITH"}
On Reservation::"ABC123" with attributes {"recordLocator": "ABC123", "holderLastName": "SMITH"}

Verbs held      LookupReservation, ReadReservation, UpdateReservation, CancelReservation
Verbs not held  ListReservations

Readable        recordLocator (public), holderLastName (public), status (public), ...
Not readable    passengers[].passportNumber (restricted), passengers[].specialServiceRequests (restricted), remarks (internal)

Writable        passengers[].seat (owner), contact.email (owner), contact.phone (owner)
Not writable    recordLocator (system), ...

The same command with the specialist's exchanged token shows the view switch of iteration 13 in one screen: remarks readable and writable, the list held, the customer's paths closed. A learner uses this to see what the policies do, then writes the case that pins it, then run-tests holds it. The two words stay apart on purpose.

6. The playground link

Cedar's playground encodes its state into the URL fragment when its share button is pressed: the policies, the schema, the entities, the context, and the three parties, as JSON, gzipped, base64. share writes the same fragment for any corpus case or request file, so a learner opens our case in Cedar's own editor, sees the same Deny, and changes a policy there before touching a file. The format is read from the site's source and is undocumented; the command's docstring says so, and if the playground changes it, only this command stops working.

$ cedar-osdc share usecases/reservations --case "co-traveler's last name is not"
a co-traveler's last name is not the holder's: the pair names one person
https://www.cedarpolicy.com/en/playground#data:H4sIA...

The link was opened in a browser during this iteration: the playground loaded the agent, the action, the reservation, the context with the co-traveler's name, and the entities, and evaluated to "Authorization denied", as the corpus says. The first version of the encoder had the three parties as strings, and the playground silently showed its default sample; the site's validator wants each as a type and an id.

7. The iteration, file by file

  • core/cli.py: the nine verbs, the use case loader, the policy name lookup from @id annotations, the caller file to bearer encoding, and the playground link.
  • pyproject.toml at the root: the package becomes installable, with cedar-osdc as its console script and core's dependencies as the project's; the numbered iterations keep their own projects.
  • core/test_cli.py: every command against the reservations use case, checking the words against the decisions the corpus and the handlers already pin, and the link's round trip.

8. Growing by tests

The commands were written against the two use cases that exist, and the first run of check-access listed the field verbs among the verbs not held, which is true and useless: the field rounds are reported by path below. The playground link was the one thing no local test could settle, so it was settled in a browser, and the test pins the round trip through our own decoder rather than the site's.

9. Installing and running it

From a fresh clone, with uv installed:

uv sync
uv run cedar-osdc run-tests usecases/reservations
uv run cedar-osdc check-access usecases/reservations --caller usecases/reservations/callers.json

The caller argument takes a caller file, one JSON object of the claims in that caller's credential; each use case ships a few under `callers/`. validate needs the official cedar command (cargo install cedar-policy-cli), and prove needs Rust and cvc5 as analysis/README.md describes. Everything else needs Python only.

10. Decisions made in this iteration

Cedar's verbs where the meaning is the same. A learner who has met the cedar command finds authorize, validate, and run-tests doing what they expect, on the same files.

Two verbs of our own, named for what they do. A dry run is a call without its effect. A check of access is a report, and it is kept apart from testing, which states expectations.

Words, not JSON. The output is for a person reading a terminal. A machine-readable form can come when something needs it.

The playground is the editor. Rather than build one, every question links to Cedar's.

11. Open questions

  1. The playground format. It is versioned, with an interface version field, and undocumented. A change breaks share alone.
  2. Tokens as files. A caller file is claims, decoded; nothing about the command reminds a learner that the real thing is signed and verified before the handler runs. The guide has to.
  3. Whether check-access should take a mode instead of a token, for a learner who does not yet know the three token shapes.
