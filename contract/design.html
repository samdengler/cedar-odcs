Cedar authorization for MCP tools, iteration 7: ODCS as source of truth

The classification map and the writers map stop being hand-written. They are generated at build time from an Open Data Contract Standard document, which is itself generated from Unity Catalog column tags. A contract change is a rebuild, never a policy edit.

1. The problem

Since iteration 3 the policies have never named a field. They look each field up in two tag maps, the classification map and the writers map, and those maps have been typed by hand into entities.json. Iteration 1's review settled where they should come from instead[1]: the response schema a tool author supplies at registration is a data contract, ODCS already defines per-field classification for it[2], and the Cedar schema and the field maps are compiled from that contract. The data behind the orders API lives in Databricks Unity Catalog, whose column tags are where the data owners record classification[3]. So the source of truth is the catalog, the interchange is the contract, and the Cedar files are a compiled artifact.

All of that happens at build time. Nothing in the request path parses a contract or calls a catalog. The enforcement point loads the same entities.json it always has; what changed is how the file came to be, and that a rebuild is the only way to change it.

2. Scope of this iteration

Built: the contract folder in this project. Two recorded Unity Catalog API responses; unity_import.py, which merges them into an ODCS v3.2.0 document; generate.py, which validates the document and emits the two tag maps and the resource entity declaration; build.py, which runs both stages and assembles entities.json and the Cedar schema; eight build tests; five corpus cases with all sixty-four prior cases carried; and the same twenty-four properties as iteration 6 proven against the generated schema. The policies are iteration 6's, unchanged.

Not built: live calls to a Databricks workspace (the responses are recorded fixtures in the real API shapes), nested objects and arrays, more than one table per contract, contract versioning and rollout, generation of policies from the contract's roles section, and any use of Databricks automatic classification tags.

3. The build, from catalog to policy input

Two stages, one command. The first reads the catalog and writes the contract; the second reads the contract and writes the Cedar inputs. Every output is committed, so the diff of a rebuild is the review of a contract change, and a test fails when the committed files are behind their sources.

The catalog does not hand over everything in one call. The tables endpoint describes the columns, their types, and their comments, and carries no tags; the entity tag assignments endpoint returns the tags[4]. Stage one reads both. The open-source contract CLI's Unity importer reads only the first and maps only comments[5], which is why the merge is written here rather than borrowed.

4. Column tags in Unity Catalog

Unity Catalog has no column-level write privilege and no classification field; it has column tags, key and value strings set by whoever holds the tagging permission on the table, and governed tags whose values an account administrator restricts to a list[3]. Four tag keys carry everything the build needs:

Tag keyValuesBecomesIf absent
classificationpublic, internal, confidential, restrictedthe property's classification; the classification mapthe build fails
writerowner, system, or a role namea writer custom property; the writers mapsystem: writable by nobody
field_namethe API field namethe property's namethe column name camel-cased
cedar_entity_typea Cedar entity typean attribute of the resource entity in the schemathe column is a field, not an attribute

The recorded tag assignments for the orders table, in the shape the endpoint returns them:

{
  "entity_type": "columns",
  "entity_name": "commerce.sales.orders.shipping_address",
  "tag_key": "classification",
  "tag_value": "confidential",
  "update_time": "2026-09-14T12:00:00Z",
  "updated_by": "orders-data-owners",
  "source_type": "MANUAL"
}

An unclassified column fails the build. The onboarding questions in the README say the contract must be complete before a tool is onboarded, and build time is the place to find out it is not; a missing tag at runtime would strip the field silently forever. A missing writer tag, by contrast, defaults to system, because unwritable is the safe reading of "nobody said".

Databricks also classifies columns automatically, with governed tags such as class.email_address and class.credit_card that a scanning agent applies[6]. Those are detectors of what a column contains, not decisions about who may see it. The build ignores them for now; an open question below proposes using them as a check on the authored level.

5. The contract

Stage one writes order.odcs.yaml, a real ODCS v3.2.0 document. The header says it is generated and where to change it. One property, as written by the build:

- name: shippingAddress
  physicalName: shipping_address
  logicalType: string
  physicalType: string
  required: false
  classification: confidential
  customProperties:
  - property: writer
    value: owner
  description: Delivery address

Classification is the spec's own field, a free-text string the spec's examples fill with exactly these words[2]. Writability has no field in the spec, so it travels as a custom property, the spec's extension point at every level. The owner reference does the same:

- name: owner
  physicalName: customer_id
  logicalType: string
  physicalType: string
  required: true
  classification: public
  customProperties:
  - property: writer
    value: system
  - property: cedarEntityType
    value: User
  description: Customer who placed the order

The document also records its server, type: databricks with the catalog and schema, and two custom properties naming the source table. Stage two validates the whole document against the Pydantic model published for the standard[7] before reading a field from it.

6. What is generated

The two tag maps, now with nine entries each, two more than iteration 6 typed. owner is declared public so it survives filtering of the owner's own order, and estimatedDelivery is a column the catalog has that no earlier iteration knew:

{ "uid": { "type": "Contract", "id": "Order" },
  "tags": {
    "id": "public",
    "owner": "public",
    "status": "public",
    "total": "public",
    "shippingAddress": "confidential",
    "cardLast4": "confidential",
    "internalNotes": "internal",
    "fraudScore": "restricted",
    "estimatedDelivery": "public"
  } }

And the resource entity declaration, with one attribute for the one property that references an entity:

entity Order {
  owner: User
};
entity Contract tags String;

The build assembles that fragment between two hand-written ones, principals.cedarschema (roles and users, which no data contract describes) and actions.cedarschema (the tool's verbs and their context, which come from tool registration). The result is the schema the prover uses for this iteration, and a test shows it equals the schema iteration 6 wrote by hand, whitespace aside.

7. The iteration, file by file

  • unity/orders.table.json and unity/orders.column_tags.json are recorded responses of the two catalog endpoints, in their real shapes, standing in for live calls.
  • unity_import.py is stage one: contract_from_unity(table, assignments) merges the two responses into the contract dict and raises ContractError on an unclassified column or an unknown level.
  • order.odcs.yaml is stage one's output, committed.
  • generate.py is stage two: contract_entities emits the two tag maps and checks that every writer is owner, system, or a role the facts know; entity_schema emits the entity declarations.
  • facts.json holds the sample users, roles, and orders from iteration 6, everything in entities.json that a contract does not describe.
  • principals.cedarschema and actions.cedarschema are the hand-written schema fragments.
  • build.py runs both stages and writes order.odcs.yaml, generated/contract.entities.json, generated/order.entities.cedarschema, generated/orders.cedarschema, and entities.json. It returns the outputs as text first, so the tests can compare without writing.
  • policies.cedar is iteration 6's file, unchanged: the point of the iteration is that it did not need to change.
  • tests/bola.json through tests/on-behalf-of.json are carried byte for byte. tests/contract.json adds five cases about the generated maps.
  • test_build.py pins the build: committed artifacts are current, the contract validates, every entry iteration 6 wrote by hand is carried with the same value, the generated schema equals the hand-written one, and an incomplete catalog fails the build.

8. Growing by tests

The corpus cases came first, and the first of them is the iteration's claim in one line: alice reads estimatedDelivery, Allow, by policy3, a policy written in iteration 3 that has never heard of the field. The field is on because the catalog declares it public and the build put it in the map. The fourth case is the writer default at work: nobody tagged a writer for the column, so the owner may not set it. The fifth is the fail-closed invariant restated against the generated map: promoCode, in no map, is stripped.

The build tests were written before the build. The drift test in particular shaped it: build() returns every output as text so the test can regenerate in memory and compare with what is committed, which is also why the generated YAML is rendered deterministically, keys in the spec's order.

9. Proved as well as tested

The prover runs iteration 6's twenty-four properties again, this time against the schema the build wrote rather than one typed in analysis/schemas/. Because the tag proofs hold for every possible tag map, nothing about the generated map's contents needs proving; what the run establishes is that the generated schema types the policies and admits the same guardrails as the hand-written one. Findings and instructions are in analysis/README.md.

10. Running it

The build, from the iteration's directory:

cd contract && uv run python build.py

From the repository root, every iteration's tests run in one command, the build tests included; and the proofs run from analysis/:

uv run pytest -v
cd analysis && cargo run

11. Decisions made in this iteration

Build time, never runtime. The catalog is read and the contract is parsed when the artifact is built. The enforcement point loads committed files. A deployment carries a specific build of entities.json and the schema.

An unclassified column fails the build. A gap in the contract is found before onboarding, where it can be fixed, instead of being masked at runtime.

A missing writer means system. Unwritable is the safe default; making a field writable is an explicit tag.

Classification levels are a fixed set; writer values are checked against the roles. A typo in either fails the build. The governed tag feature of Unity Catalog can enforce the same list at the source.

The policies are not generated. They never name a field, so they did not need to be. Whether the contract's roles section should one day generate the grants is an open question.

Verbs and principals are hand-written schema fragments. A data contract describes data. The tool's verbs come from tool registration and the principal types from the identity setup; the build concatenates the three.

12. Open questions

  1. Automatic classification as a check. A column carrying a Databricks class.* tag for a card number or an email address, with an authored level of public, is probably a mistake. The build could fail on that disagreement. Which detector tags imply which minimum level is a governance decision, not a build rule.
  2. Contract versioning and rollout. The document carries a version and the build is deterministic, but nothing yet ties a deployed enforcement point to a contract version, or says what happens to in-flight tool registrations when a field is reclassified.
  3. Field names. The API's field names and the table's column names differ, and the field_name tag bridges them one column at a time. If the API's response schema is registered separately, that schema is the better source for names, and the contract's physicalName would link the two.
  4. Generating grants from the contract. ODCS has a roles section with a free-text access field. It could carry which roles hold which levels and verbs, and the build could emit the role policies. That would move the last hand-written governance artifact into the contract, at the cost of a policy generator that itself needs proving.
  5. Nested payloads and multiple tables. The importer handles one flat table. ODCS supports nested properties; the field filter from iteration 3 does not yet.

Glossary

TermMeaning
ODCSOpen Data Contract Standard, a YAML format for describing a dataset, its properties, and their classification. Version 3.2.0 here.
Unity CatalogThe Databricks catalog that holds the tables behind the orders API and, in column tags, their classification.
Column tagA key and value string attached to a column in Unity Catalog. The build reads four keys.
Governed tagA Unity Catalog tag whose allowed values an administrator restricts, enforcing the classification list at the source.
Stage one, stage twoCatalog to contract; contract to Cedar. Both in build.py.
Drift testThe test that regenerates every artifact in memory and fails if a committed file differs.
