Cedar authorization for MCP tools, iteration 5: function level authorization (API5)

Two new verbs that belong to roles, a refund nobody but finance can issue, and the first role-granted write path: support may now update any order, but only the fields whose writer names the role.

1. The problem

Every rule so far has been about an object or a field of it. The remaining threat in scope is about the verb. A tool that exposes RefundOrder next to ReadOrder lets any caller who can reach the tool try either, and an upstream API with no governance of its own will issue the refund. OWASP calls this API5, broken function level authorization (BFLA)[1]: a caller invoking an operation reserved for another role. Ownership does not help here. Alice owns order 1001 and still must not refund it; that is a finance decision.

Iteration 2 met this threat as an absence. Carol on the support desk could read any order, and no policy permitted her to update one, so UpdateOrder fell to default deny: a role that holds read does not thereby hold write. This iteration states the rule in the positive. Roles hold verbs, one at a time, and a verb held implies no other.

2. Scope of this iteration

Built: the function-level folder in this project. The six policies from iterations 1 through 4 plus five verb and role policies, a finance role and a member of it, one revised writer value, a check_call gate that runs the whole request leg (verb round, then payload round), fourteen new corpus cases with all thirty-five prior cases carried, one of them revised, and twenty properties proven in analysis/.

Not built: verbs whose permission depends on the order's state (cancelling a shipped order), action groups, ReplaceCard, on behalf of access, ODCS parsing, and Gateway integration.

3. Roles hold verbs

Two verbs are added. CancelOrder belongs to the order's owner and to support. RefundOrder belongs to a new finance role and to nobody else. The refund policy is the whole of API5 in four lines:

@id("finance-refunds-any-order")
permit(
  principal in Role::"finance",
  action == Action::"RefundOrder",
  resource
);

The interesting decisions are the ones no policy makes. Alice asking to refund her own order matches nothing, because the ownership policies name ReadOrder, UpdateOrder, and CancelOrder, never RefundOrder. Carol asking to refund matches nothing, because the support role holds read, cancel, and update. And Dave in finance asking to read an order matches nothing either: holding refund does not imply read. Each verb is granted on its own line, and the corpus pins every cross-verb attempt as Deny.

VerbOwnerSupportFinance
ReadOrderown ordersany orderno
UpdateOrderown ordersany order (new)no
CancelOrderown orders (new)any order (new)no
RefundOrdernonoany order (new)

On the request leg the verb round runs first. A denied verb rejects the call before any payload is examined; the payload round from iteration 4 runs only for an update the verb round allowed.

4. The role-granted write path

Iteration 4 left one question open: support plausibly should update internalNotes, and doing so would need a role-granted object-level update, a writer value naming the role, and a knowing revision of the guardrail that said writes require ownership. This iteration does all three. The object-level permit is the same pattern as support's read:

@id("support-updates-any-order")
permit(
  principal in Role::"support",
  action == Action::"UpdateOrder",
  resource
);

On its own that permit would let support set any field the payload round allows, and the payload round of iteration 4 only knew two writers, owner and system. The writers map gains a third value, and one entry changes:

{ "uid": { "type": "Contract", "id": "Order/writers" },
  "tags": {
    "id":              "system",
    "status":          "system",
    "total":           "system",
    "shippingAddress": "owner",
    "cardLast4":       "system",
    "internalNotes":   "support",
    "fraudScore":      "system"
  } }

The field policy for the role looks the field up the same way the owner's does, asking for its own name:

@id("support-updates-support-fields")
permit(
  principal in Role::"support",
  action == Action::"UpdateOrderField",
  resource
) when {
  context has field &&
  Contract::"Order/writers".hasTag(context.field) &&
  Contract::"Order/writers".getTag(context.field) == "support"
};

So carol's payload of {internalNotes, shippingAddress} is rejected whole, naming shippingAddress: the object-level permit opened the door, and the writers map says which fields are behind it. The owner's field policy still asks for owner, so alice loses nothing and gains nothing from the change; internalNotes was unwritable for her before and stays so.

5. The iteration, file by file

  • policies.cedar carries the six prior policies verbatim and appends P7 through P11: owner cancels, support cancels, finance refunds, support updates at object level, support updates support fields. The two new object-level ownership policies guard the owner access with has, so a guessed order id fails closed with no evaluation error; iterations 1 and 2 left theirs unguarded, and the analysis reveal shows the difference.
  • entities.json adds Role::"finance" and User::"dave" in it, and changes the writer of internalNotes from system to support. Nothing else moves.
  • request_gate.py assembles the request leg. check_call(principal, action, resource, body) asks the verb first and, for an update that passes, one question per payload field: 
    if not is_allowed(principal, action, resource).allowed:
    return CallDecision(allowed=False, denied_verb=True)
field_action = FIELD_ACTIONS.get(action)
if field_action is None or not body:
    return CallDecision(allowed=True, denied_verb=False)
denied = [
    name
    for name in body
    if not is_allowed(principal, field_action, resource, {"field": name}).allowed
]
return CallDecision(allowed=not denied, denied_verb=False, denied_fields=denied)
  • tests/bola.json, tests/field-reads.json, and tests/field-writes.json are carried byte for byte. tests/bola-writes.json is carried with one case revised, described in the next section.
  • tests/function-level.json adds fourteen cases: the two allows per new verb, every cross-verb attempt (owner refunds, support refunds, finance cancels, finance reads), the role-granted update and its bound (internalNotes allowed, total denied, finance denied on internalNotes), the unknown principal, and the guessed order id.
  • test_corpus.py is the same runner, unchanged. test_gate.py pins the enforcement: a denied verb rejects before the payload is read, and a role-granted update is rejected whole when the payload reaches past the writers map.

6. Growing by tests

The fourteen cases were written first, then the five policies and the one map entry. For the first time, the carried corpus did not pass unchanged. Iteration 2 pinned this case:

{
  "description": "support agent may read any order but update none: no write permit exists",
  "principal": { "type": "User", "id": "carol" },
  "action":    { "type": "Action", "id": "UpdateOrder" },
  "resource":  { "type": "Order", "id": "order-1001" },
  "decision":  "Deny"
}

Granting the role the verb flips it to Allow, and the runner failed on it exactly as the method promises: a defense recorded as a test fails the moment a change weakens it. The change is intended, so the case is revised rather than deleted, and its description says which iteration revised it and what the decision was before:

{
  "description": "support agent may update any order: revised in iteration 5, which grants the role the verb (Deny through iteration 4)",
  "principal": { "type": "User", "id": "carol" },
  "action":    { "type": "Action", "id": "UpdateOrder" },
  "resource":  { "type": "Order", "id": "order-1001" },
  "decision":  "Allow",
  "reason":    ["policy9"]
}

The rule this sets: a carried decision changes only through a revised case whose description records the revision, and the design document of the revising iteration names it. Iteration 2's own corpus stays as it was in bola-writes/; the revision lives in the iteration that made it.

7. Proved as well as tested

Four new guardrails hold over every possible request and every possible role membership:

  • Refund requires finance. Nobody outside the role ever refunds: not an owner, not support.
  • Cancel requires owner or support. Finance holds refund, not cancel.
  • Role writes only role fields. Through the support role, a field is writable only when the writers map names support. This replaces iteration 4's writes-require-ownership, retired knowingly by this iteration's object-level permit.
  • The finance role grants no read. A finance member reads an order only by owning it or through another role that holds the verb.

The last one was falsified on its first try. Written as "finance reads only as owner", the prover produced a principal who is in both the finance and support roles and reads through support. Role membership is not exclusive, the same lesson the support-never-updates guardrail taught in iteration 2, and the invariant that holds is about the role, not the person. Two guardrails from earlier iterations are retired: support-never-updates and writes-require-ownership no longer hold, by design. The five that still apply are carried and reproven against the eleven-policy set. Findings and instructions are in analysis/README.md.

8. Running it

From the repository root, every iteration's tests run in one command:

uv run pytest -v

The iteration also runs standalone, and the proofs run from analysis/:

uv run --project function-level pytest -v
cd analysis && cargo run

9. Decisions made in this iteration

Verbs are granted one at a time. Finance holds refund and nothing else; the corpus pins that refund implies no read. When a use case needs finance to read orders, that is one more permit and one more field policy naming the levels finance holds, not an implication.

A role-granted update is bounded by the writers map. The object-level permit says the role may update orders; the writer value says which fields. Widening support's writes to another field is a map change, reviewable as data, not a policy change.

A carried decision changes only through a revised case. The revised case keeps the old decision in its description. The regression gate is not weakened silently, and the diff of the corpus is the record of what governance changed.

New ownership policies guard the owner access. The reveal in analysis/ shows why: under a schema where the store may not know an order, the unguarded policies of iterations 1 and 2 are rejected by the validator and the guarded ones pass. The old policies are left as they are, so the reveal keeps showing the gap.

10. Open questions

  1. State-dependent verbs. Whether an order can be cancelled depends on its status; a shipped order cannot. That rule needs the order's attributes at decision time, which on the request leg means the same pre-fetch question iteration 2 raised for ownership. The data contract will say which attributes exist; where they come from is the enforcement placement iteration's business.
  2. Action groups. Cedar lets actions have parents, so a policy could grant Action::"OrderWrites" and cover update, cancel, and future verbs at once. With four verbs the per-verb lines read better. Revisit when the verb list comes from the contract.
  3. Where verb rules run. The verb round needs only the caller's roles and the tool name, both known before the upstream call. That makes it the one round that could run in a request-leg policy engine with no entity data at all, ahead of the interceptor. Iteration 10 weighs this.
  4. What a rejection reveals, carried from iterations 2 and 4. A "verb not held" rejection tells a caller the verb exists.

Glossary

TermMeaning
BFLABroken function level authorization, OWASP API5: a caller invoking an operation reserved for another role, such as a refund.
VerbAn operation a tool exposes, modeled as a Cedar action: ReadOrder, UpdateOrder, CancelOrder, RefundOrder.
Verb roundThe first question on the request leg: may this principal perform this verb on this order. Covers API1 and API5 together.
Payload roundThe second question, one per field, for an update the verb round allowed. From iteration 4.
Role-granted writeAn update permitted through role membership rather than ownership, bounded by writer values that name the role.
Revised caseA carried corpus case whose decision an iteration changed on purpose, with the old decision kept in its description.
