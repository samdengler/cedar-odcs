Cedar authorization for MCP tools, iteration 3: broken object property level authorization (API3)

Iterations 1 and 2 gated whole tool calls: may this principal read, or update, this object. Iteration 3 asks a second round, one question per field in the response, and strips every field that comes back Deny.

1. The problem

Iteration 1 made objects unreachable without a stated relationship: alice cannot fetch bob's order by swapping an id, and an unknown principal gets nothing. But an object a caller is allowed to read still carries fields that caller should not see. Alice may read her own order, and the upstream response includes the support team's internalNotes and a fraudScore. Carol on the support desk may read any order, and the response includes the customer's shippingAddress and cardLast4. The upstream API returns every field to any authenticated caller; in OWASP terms this is API3, broken object property level authorization[1].

Field-level enforcement has to happen on the response leg. The fields do not exist until the upstream API has answered, so the request leg has nothing to filter. This iteration stays standalone Python, like its predecessors, and builds directly on iteration 2's files.

2. Scope of this iteration

Built: the field-reads folder in this project. The three object-level policies from iterations 1 and 2 plus two field policies, the field classification facts, a filter_response wrapper that strips denied fields from a payload, and 28 pytest tests, all passing, with the twelve object-level cases carried unchanged.

Not built: function level checks (API5), any parsing of ODCS documents, mask caching, and any integration with AgentCore Gateway or Runtime. Nested payloads and lists are also out; this iteration filters a flat object.

3. The second round of questions

The request leg keeps the object-level checks from iterations 1 and 2. The response leg is new. For each field in the payload the wrapper asks one more question, with a new action and, for the first time, a non-empty context. Here is one such question as it appears in the test corpus, together with the expected decision:

{
  "principal": { "type": "User", "id": "carol" },
  "action":    { "type": "Action", "id": "ReadOrderField" },
  "resource":  { "type": "Order", "id": "order-1001" },
  "context":   { "field": "cardLast4" },
  "decision":  "Deny"
}

Fields that come back Deny are removed from the payload; the rest passes through untouched. Per the direction settled in iteration 1's review, the wrapper never rejects a response outright: it strips, and it reports what it stripped so the enforcement point can log the removals.

The naive loop evaluates Cedar once per field per response. Iteration 1's review already settled how that cost is bounded: field permits depend on role and classification rather than row values, so the field mask for a caller can be computed once and cached. This iteration keeps the loop because it is the readable version of the idea; the caching belongs to the enforcement-placement iteration.

4. Classification lives in the facts

The field policies never name a field. They look the field up in a classification map and ask whether its level is one the policy grants:

@id("customer-fields-on-own-order")
permit(
  principal,
  action == Action::"ReadOrderField",
  resource
) when {
  resource has owner &&
  resource.owner == principal &&
  context has field &&
  Contract::"Order".hasTag(context.field) &&
  ["public", "confidential"].contains(Contract::"Order".getTag(context.field))
};

The map itself is data, recorded in entities.json with the rest of the facts as entity tags on one Contract entity. Tags, added in Cedar 4.2[3], are a key-value map an entity carries alongside its attributes. Attribute names must be fixed when a schema is written; tag keys are looked up dynamically with hasTag and getTag, which is what field names need. The policies are written once, and the set of fields stays data:

{ "uid": { "type": "Contract", "id": "Order" },
  "tags": {
    "id":              "public",
    "status":          "public",
    "total":           "public",
    "shippingAddress": "confidential",
    "cardLast4":       "confidential",
    "internalNotes":   "internal",
    "fraudScore":      "restricted"
  } }

Each field carries exactly one of four classification levels: public, internal, confidential, restricted. The contract classifies; the policies grant levels to readers. The wrapper passes the field name into the request context as a plain string. The grants in this iteration:

Readerpublicinternalconfidentialrestricted
owner, on an order they ownyesyes
support, on any orderyesyes

Two consequences fall out of this design.

Undeclared fields fail closed. If the upstream response grows a field the contract never declared, say debugTrace, the lookup fails the hasTag guard, no permit matches, and default deny strips the field. The invariant from iteration 1's review, that schema drift strips rather than leaks, needs no code of its own.

A declared field can still be readable by nobody. fraudScore is restricted, and no policy grants restricted, so every caller loses it. When a fraud role exists, one permit granting it the restricted level turns the field on, with no change to the map.

The has guards are also new. The ownership policies of iterations 1 and 2 evaluate resource.owner directly, and their corpora pin the resulting evaluation errors when the order does not exist. The field policy guards with resource has owner, so a guessed order id fails to a clean Deny with no error. Both behaviors stay tested: the old policies are carried unchanged, errors and all, and the new corpus pins the guarded behavior.

5. The iteration, file by file

Everything from iteration 1 is recognizable; each file grew in one direction.

policies.cedar carries the three object-level policies verbatim and appends P4 (public and confidential fields on an owned order) and P5 (public and internal fields for support). Appending matters: cedarpy reports determining policies by position in the file (policy0, policy1, …), the corpus refers to those ids, and inserting a policy would renumber every case after it.

entities.json carries iteration 1's users, role, and orders, and adds one Contract entity whose tag map is the hand-written stand-in for a contract's classification column. This file is the one ODCS will eventually generate, and the tag map is a near transcription of a contract's property list.

field_filter.py replaces authorizer.py as the enforcement wrapper. is_allowed is the same function with a context parameter added. filter_response(principal, resource, body) is the response leg: one question per field, returning the kept body and the list of stripped field names.

for name, value in body.items():
    if is_allowed(principal, 'Action::"ReadOrderField"', resource, {"field": name}).allowed:
        kept[name] = value
    else:
        stripped.append(name)

tests/bola.json and tests/bola-writes.json are the corpora of iterations 1 and 2, byte for byte. They run against the grown policy and entity files and must keep passing; they are the regression gate proving the appended policies change no object-level decision.

tests/field-reads.json adds twelve ReadOrderField cases: the owner's allows and denies, the support matrix, API1 re-checked at field level, and the two fail-closed cases (undeclared field, guessed order id).

test_corpus.py is the same runner, unchanged. test_filter.py is new: it feeds one full upstream payload to filter_response and asserts exactly which fields each caller keeps, that stripped names are reported, and that surviving values pass through unmodified.

6. Growing by tests

The loop from iteration 1 held: the twelve corpus cases were written first as the statement of the rule, then the policies and facts that make them pass. The corpus stays engine-independent data in the cedar-integration-tests format[5], so the future Rust enforcement build runs the same JSON against the same rules.

The division of labor between the two test files is worth keeping for later iterations. The corpus pins decisions: one PARC question, one expected answer, expected determining policies. test_filter.py pins enforcement: what a payload looks like after the decisions are applied. The first is portable across engines; the second is specific to the enforcement point and will eventually be the contract for the Rust extension's response rewriting.

7. Running it

From the repository root, every iteration's tests run in one command:

uv run pytest -v

The iteration also runs standalone:

uv run --project field-reads pytest -v

8. Decisions made in this iteration

Classification is a tag map on a contract entity, and the field travels as a plain string. Two alternatives were considered. Listing field names inside the policy text (["id", "status", "total"].contains(context.field)) puts data facts in policy code and turns every contract change into a policy change. One Field entity per field, grouped into FieldClass entities via parents, keeps classification in the facts and was the first working version of this iteration; it costs an entity per field, an id naming convention (Field::"Order/cardLast4"), and an entity-reference escape in the request context. Entity tags keep classification in the facts and drop those costs: one entity per contract, and the context carries the field name as a string. What tags give up is hierarchy, since levels are strings rather than entities that could nest under in; nothing planned needs that.

Classification uses four levels: public, internal, confidential, restricted. Each field carries exactly one, so the tag value is a single string. The division of responsibility follows: reclassifying a field is an entities change, reviewable as data; granting a reader a level is a policy change. An earlier version named classes for audiences (customer-visible, operational) and let one field carry several; a single sensitivity level per field says less per entry but matches how ODCS contracts classify properties, which is what the map becomes in iteration 5.

Strip and report, never reject. filter_response returns the filtered body plus the stripped names, matching the review decision that the interceptor never refuses a whole response. Logging the removals is the caller's job; surfacing them to tool authors stays open.

The policy file is append-only. Positional policy ids are load-bearing in the corpus, so new policies go at the end. The @id annotations name policies for human readers; the corpus keeps using positional ids because that is what cedarpy reports.

9. Open questions

  1. Nested payloads and lists. This iteration filters one flat object. Real order payloads nest (items[].sku), which needs a naming convention for tag keys and a walk of the payload tree. Deciding it belongs with ODCS, since contracts already name nested properties, and with row filtering for the list case.
  2. Whether ReadOrderField stays a per-resource-type action or becomes a single ReadField action once a second resource type exists.
  3. Carried from iteration 1: how stripped-field removals are surfaced to tool authors, and measured response-path overhead once mask caching exists to measure against.

Glossary

TermMeaning
API3Broken object property level authorization, OWASP API3. Receiving fields inside an allowed object that this caller should not see.
Entity tagsA key-value map a Cedar entity carries alongside its attributes, looked up with hasTag and getTag. Unlike attribute names, tag keys are dynamic.
Contract entityThe entity holding one data contract's classification map as tags: field name to classification level, such as Contract::"Order".
Classification levelOne of public, internal, confidential, restricted. Each field carries exactly one; policies grant levels to readers.
ContextThe C in PARC: extra facts about one request. First used in this iteration, to carry the name of the field being asked about.
Fail closedA field the facts do not declare matches no permit and is stripped, so drift removes data instead of leaking it.
MaskThe set of fields a given caller keeps. Computable per caller and contract version, which is what makes caching possible later.
