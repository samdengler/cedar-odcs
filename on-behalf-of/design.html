Cedar authorization for MCP tools, iteration 6: on behalf of access modes

A customer acting directly, an employee acting directly, and an employee acting for a customer. The principal is always the actor; the context carries whom they act for; and every policy from the first five iterations gains a mode without changing a single direct-mode decision.

1. The problem

An agent helping a customer is driven by an employee on the support desk as often as by the customer. The employee's own credential lets carol read any order and its internal notes. When she is working alice's case, though, the request is alice's: it should reach alice's order and alice's fields, and nothing of bob's, and nothing internal. Iteration 1's review settled the model for this[1]: the system implements on behalf of (OBO) access, the principal stays the actual actor, the context carries whom they act for, employee-only permits require direct mode, and ownership permits evaluate against the acted-for party.

That review also said the requirement is stated ahead of the facts. On behalf of exists in the identity setup but is new, and today's tokens may not carry what these rules read. This iteration makes the requirement testable: each corpus case names the context its decision needs, a projection turns token claims into that context, and the claims it reads are listed with their status, so the identity setup can be checked against the list rather than guessed at.

2. Scope of this iteration

Built: the on-behalf-of folder in this project. The eleven policies from iterations 1 through 5, each revised for mode, plus one forbid; an employee role that support and finance belong to; a project function from token claims to the Cedar request and the principal's role facts; three hand-written token payloads, one per mode; fifteen new corpus cases with all forty-nine prior cases carried unchanged; and twenty-four properties proven in analysis/.

Not built: token verification (signature, issuer, audience; the Gateway's authorizer does that before any interceptor runs), a may_act check of which customers an employee may act for, the agent workload as a party of its own, nested delegation, ODCS parsing, and Gateway integration.

3. Three modes, one principal

The Cedar principal is the actor: the party whose credential made the call. In direct mode that is all there is. In on behalf of mode the context carries one more entity, actingFor, the party the actor works for. Here is a delegated request as it appears in the corpus:

{
  "description": "employee for customer: support acting for alice reads alice's order through alice's ownership",
  "principal": { "type": "User", "id": "carol" },
  "action":    { "type": "Action", "id": "ReadOrder" },
  "resource":  { "type": "Order", "id": "order-1001" },
  "context":   { "actingFor": { "__entity": { "type": "User", "id": "alice" } } },
  "decision":  "Allow",
  "reason":    ["policy0"]
}

The allow comes from policy0, the ownership policy from iteration 1; no support policy fires. That is the model in one case: while acting for alice, carol holds alice's access, and alice's access is what the ownership policies grant.

The context is a projection of the token. OAuth 2.0 Token Exchange[2] defines a delegated token whose subject (sub) is the party on whose behalf the request is made and whose actor claim (act) names the party making it. The projection in claims.py reads that:

act = claims.get("act")
if act is None:
    actor_sub = claims["sub"]
    roles = claims.get(ROLE_CLAIM, [])
    context = {}
    mode = "employee-direct" if roles else "customer-direct"
else:
    actor_sub = act["sub"]
    roles = act.get(ROLE_CLAIM, [])
    context = {"actingFor": _entity_ref(claims["sub"])}
    mode = "employee-for-customer"
principal_entity = {
    "uid": {"type": "User", "id": actor_sub},
    "attrs": {},
    "parents": [{"type": "Role", "id": role} for role in roles],
}

The projection also builds the principal entity. Role membership has lived in entities.json since iteration 1, where carol has the support role as a parent. At the Gateway there is no store to ask; the token says what roles the actor holds, so the entity is built per request from the roles claim and replaces any stored entity of the same id. A token for carol without the role claim is a carol with no role, whatever the store says, and test_claims.py pins that.

4. Every policy has a mode

No permit is added. Each of the eleven carried policies is revised by one of two rules. An ownership policy compares the owner to the acted-for party when present and to the principal otherwise:

@id("customer-reads-own-order")
permit(
  principal,
  action == Action::"ReadOrder",
  resource
) when {
  resource.owner == (if context has actingFor then context.actingFor else principal)
};

A role policy requires direct mode:

@id("support-fields-on-any-order")
permit(
  principal in Role::"support",
  action == Action::"ReadOrderField",
  resource
) when {
  !(context has actingFor) &&
  context has field &&
  Contract::"Order".hasTag(context.field) &&
  ["public", "internal"].contains(Contract::"Order".getTag(context.field))
};

Together the two rules produce the intended access without a third kind of policy. Carol acting for alice reads alice's shipping address, because the ownership field policy grants confidential fields to the owner and alice is the owner. She does not read alice's internal notes, because the only policy granting internal fields is a role policy, and role policies are off while acting. She does not reach bob's order at all. Dave in finance acting for alice reads alice's order too: the mode grants the customer's access to whichever employee holds the delegation. And dave acting for alice may not refund, because a refund is finance's own act, done in direct mode.

One forbid is appended, the first in the policy set. Only an employee may act for another party; support and finance now sit under an employee role in the facts:

@id("only-employees-act-for-others")
forbid(
  principal,
  action,
  resource
) when {
  context has actingFor &&
  !(principal in Role::"employee")
};

A customer token carrying an actor claim, or an unknown principal claiming to act for alice, matches this forbid and nothing else matters. In Cedar a forbid overrides every permit[3], and the corpus pins it as the determining policy for both.

Direct mode is untouched. Every carried case is a direct-mode request, and all forty-nine pass unchanged, which is the corpus's way of saying the revision preserved every earlier decision. The composition iteration will state the same thing as a theorem.

5. The claims the corpus needs

Every fact the policies read in this iteration comes from the token. This table is the requirement the identity setup is measured against. The status column is what is known today: each claim is an assumption until a real token confirms it, and a shortfall becomes a change request to the identity setup.

ClaimWhat the rules read from itStandardStatus
subThe principal in direct mode; the acted-for party in delegated mode. Compared to Order.owner, so it must be the same identifier the order system records as the owner.RFC 7519Assumed: that the subject identifier and the order owner identifier agree.
act.subThe principal in delegated mode.RFC 8693 section 4.1Assumed: that the identity setup issues an actor claim on delegated tokens.
roles (top level in direct mode, inside act when delegated)The principal's role parents: support, finance, and through them employee.Custom claimAssumed: the claim name, its placement on the actor, and the role names.
iss, aud, expNothing. The Gateway's JWT authorizer validates them before an interceptor runs.RFC 7519Not an authorization fact; configured, not read.
may_actNothing yet. Which parties an employee may act for would come from it.RFC 8693 section 4.4Not used; see open questions.

Two of these are the likely gaps. Whether the subject identifier matches the owner identifier is a fact about two systems, and a mismatch would make every ownership rule fail closed for every caller. And whether delegated tokens carry act at all decides whether the third mode exists as a token or only as a corpus. Both are answerable from one real token of each mode and one order record, which is the fact-finding this iteration asks for.

6. The iteration, file by file

  • policies.cedar carries the eleven policies with their ids and positions unchanged, each revised for mode, and appends the forbid as policy11. The two rules are stated once in the file's header.
  • entities.json adds Role::"employee" and makes support and finance its children. Nothing else moves; carol's and dave's role facts are what the store held, and at the Gateway the token replaces them.
  • claims.py holds project(claims), the mapping above, and is_allowed(claims, action, resource), one authorization question asked with a token instead of a principal.
  • tokens/customer-direct.json, tokens/employee-direct.json, tokens/employee-for-customer.json are hand-written payloads standing in for decoded tokens, one per mode. They are the corpus's requirement written as tokens.
  • tests/bola.json through tests/function-level.json are carried byte for byte.
  • tests/on-behalf-of.json adds fifteen cases: the two direct modes restated, the delegated reads, fields, update, and cancel on the customer's own order, the delegated refund denied, finance acting for a customer, a customer and a stranger forbidden from acting, acting for oneself, and the guessed order id while acting.
  • test_corpus.py is the same runner, unchanged. test_claims.py enters each mode through its token and checks the projection and the decisions, and pins that roles come from the token.

7. Growing by tests

The fifteen cases were written first. Adding on behalf of permits beside the carried ones and leaving the role permits alone would fail the case "internal field of alice's order is not readable while acting", because support's field permit would still fire. So the role permits carry the direct-mode condition, and the owner expression on the carried ones is conditional. The final set has the same number of permits as iteration 5.

The carried corpora held in the other direction: forty-nine direct-mode cases, none of which changed, ran against a policy set in which every policy had been edited.

8. Proved as well as tested

Three new guardrails hold over every possible request, every acted-for party, and every tag map:

  • Acting is bounded by ownership. While acting for a party, nothing is allowed outside that party's ownership, for every verb at once. Refund included: the finance role grants nothing while acting.
  • Acting reads the customer's levels only. Internal and restricted fields are never revealed through the acting mode, whoever the actor is.
  • Acting writes owner fields only. Support's own field, internalNotes, is off while acting.

Four guardrails from iterations 3 and 5 mention ownership or a role, and each is revised for mode the way the policies were: support reaches confidential fields only through ownership, own or acted-for; cancel requires the owner, an employee acting for the owner, or support in direct mode; and so on. The five mode-free guardrails are carried unchanged and reproven. Findings and instructions are in analysis/README.md.

9. Running it

From the repository root, every iteration's tests run in one command:

uv run pytest -v

The iteration also runs standalone, and the proofs run from analysis/:

uv run --project on-behalf-of pytest -v
cd analysis && cargo run

10. Decisions made in this iteration

The principal is the actor. Iteration 1's review settled it, and audit records who made the call; the acted-for party is context. The projection from a delegated token therefore swaps the parties: the token's actor becomes the principal and the token's subject becomes actingFor.

Acting for a customer holds the customer's access. Iteration 1 said "roughly the intersection" of the employee's and the customer's access. The two rules it also stated, role permits off while acting and ownership evaluated against the acted-for party, yield the customer's access: alice's fields on alice's orders, confidential ones included. A strict intersection would drop the confidential fields, which are what an agent helping alice needs, so the two rules are taken as the definition and the intersection reading is recorded here as the alternative.

Mode is a revision of every policy. Every carried decision is preserved, and the policy set stays the size it was.

Roles come from the token. The principal entity is built per request from the role claim. The store's role facts are for the corpus; the Gateway has no store to ask.

The claims are listed with their status. Each one assumed until a real token shows it. The list is the gap analysis's input; the identity setup is measured against it.

11. Open questions

  1. Which customers an employee may act for. The rules accept any employee acting for any customer; the identity setup decides who gets a delegated token. RFC 8693's may_act claim could carry the allowed parties, and a forbid would read it. Left until the claims inventory says whether the setup issues it.
  2. The agent as a party. The workload that calls the tool has an identity of its own, and the Gateway's token exchange carries both the agent's and the caller's identity[4]. The rules here name the human actor and the customer only. Whether a policy should ever depend on which agent is calling is the enforcement placement iteration's question.
  3. Acting for oneself. An employee whose delegated token names themselves lands in the acting mode with the role off. The corpus pins that as Deny for an order they do not own. Whether the projection should treat it as direct mode instead is a choice for the identity setup's conventions.
  4. Identifier alignment between the token subject and the order owner, from the claims table. The one fact that cannot be settled inside this repository.
