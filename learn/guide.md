# The guide

What you need to know about your own domain to fill in a use case,
the three policy shapes the project has, and the command line. The
[learning path](README.md) shows all of this running; this page is
the reference.

## Six questions about your domain

Every use case is a tool, the API behind it, and the rules that
govern it. These questions decide what goes in the descriptor and the
contract. Facts come from the token and the tool input first; a
lookup is added only for a gap the answers prove.

1. **Identity.** What bearer token reaches the Gateway, and whom does
   its subject identify: a customer, an employee, or the agent itself?
   Which claims carry roles, and is there an actor claim for acting
   on behalf of someone? If customers have no identity, as with a
   reservation held by locator and last name, say so: the customer
   becomes presented facts, never a principal.
2. **Verbs.** Which operations does the tool expose, and which are
   reads and which are writes? Writes are gated on the request leg
   before the call; reads are filtered on the response leg.
3. **Rules and their facts.** For each rule, which facts decide it?
   Which are in the token or the tool input already? Which live only
   in the record, like an owner or a holder's name? A rule that needs
   the record decides on the response leg for reads, and after a
   pre-fetch for writes.
4. **Data contract.** What does the response contain, field by field,
   nested fields included, and what level does each carry? A field
   outside the contract is stripped, so the contract must be complete
   before onboarding.
5. **Writers.** Which fields may a caller set, and which caller: the
   owner, a role, or nobody?
6. **Grants.** Which roles hold which verbs, and which levels does each
   reader hold?

## What a use case directory holds

| File | Answers | Notes |
|---|---|---|
| `usecase.py` | 1, 2, 3 | the descriptor: entity type, which payload fields are attributes and of what type, the id field, the verbs of each round, the tool table, and for writes that need the record, the verbs and a fetch function |
| `unity/*.json` | 4, 5 | the table and its column tags as Unity Catalog returns them; `classification`, `writer`, `field_name`, `cedar_entity_type`, `cedar_attribute_type`; nested levels as `classification__<field>` on the column |
| `*.odcs.yaml`, `generated/` | 4, 5 | generated by `cedar-osdc build`, committed, drift-tested |
| `facts.json` | 1 | sample users, roles, and records for the corpus |
| `principals.cedarschema`, `actions.cedarschema` | 1, 2 | hand-written: who can be a principal, and the verbs with their context |
| `policies.cedar` | 6 | the grants; no policy names a field |
| `tests/*.json` | 3, 6 | the corpus, one request and its expected decision per case |
| `callers/*.json` | 1 | the claims of one caller's credential per file |
| `events/*.json` | 2 | Gateway events for the dry run and the tests |

## The three policy shapes

Every policy in the project is one of these. Copy the one you need
and change the names.

**Ownership.** The record names its owner, and the caller is the
owner. From hello:

```cedar
@id("owner-reads-own-note")
permit(
  principal,
  action == Action::"ReadNote",
  resource
) when {
  resource has owner &&
  resource.owner == principal
};
```

**Possession.** The caller presents facts, and the record confirms
them. From reservations:

```cedar
@id("read-by-possession")
permit(
  principal,
  action == Action::"ReadReservation",
  resource
) when {
  context has presented &&
  resource has recordLocator &&
  resource has holderLastName &&
  resource.recordLocator == context.presented.locator &&
  resource.holderLastName == context.presented.lastName
};
```

**A role holding a verb, or a role holding levels.** The caller is in
a role, and the role grants the verb or the levels. From orders, the
field form, with the acting-mode condition that turns the role off
while acting for a customer:

```cedar
@id("support-fields-on-any-order")
permit(
  principal in Role::"support",
  action == Action::"ReadOrderField",
  resource
) when {
  !(context has actingFor) &&
  context has field &&
  Contract::"Order".hasTag(context.field) &&
  ["public", "internal"].contains(Contract::"Order".getTag(context.field))
};
```

A field policy of any shape ends the same way: the field is looked up
in the map by path, and the policy names the levels it grants, or the
writer it requires. Nested fields are paths: `contact.email`,
`passengers[].seat`.

Two rules that are not shapes but habits. Guard every attribute read
with `has`, so a record the store does not know fails closed instead
of raising an error. And write a forbid for an invariant you rely on,
under `analysis/guardrails/`, so the prover holds it over every
request; the [proofs page](proofs.md) says what that gives you.

## Caller files

A caller file is a JSON object of claims, standing in for the JWT the
Gateway has verified. It is named for who is calling, and it has
nothing to do with the tokens a language model counts. The projection reads:

| Claim | Meaning |
|---|---|
| `sub` | the principal, or, when `act` is present, the human acted for |
| `act.sub` | the actor when the token was exchanged: the agent, typically |
| `roles` | the subject's roles, added to the store's |
| `client_id` equal to `sub` | a workload token: the principal is an `Agent` |

These are the claims the project assumes; the identity setup confirms
them. Presented facts such as a locator and a last name are not
claims: they come from the tool arguments the tool table names.

## The command line

```sh
uv sync                                   # once, at the repository root
uv run cedar-osdc run-tests DIR           # the corpus, every case named
uv run cedar-osdc authorize DIR --principal ... --action ... --resource ...
uv run cedar-osdc dry-run DIR --caller C.json --tool NAME --arg k=v [--response FILE]
uv run cedar-osdc check-access DIR --caller C.json [--presented k=v] [--record FILE]
uv run cedar-osdc share DIR --case "text from a case description"
uv run cedar-osdc build DIR               # catalog to contract to Cedar
uv run cedar-osdc validate DIR            # needs: cargo install cedar-policy-cli
uv run cedar-osdc prove                   # needs Rust and cvc5; see analysis/README.md
```

`run-tests`, `authorize`, and `validate` do what the official `cedar`
command's verbs of the same names do, on the same files. `dry-run` and
`check-access` are this project's: one tool call through both legs
without calling the tool, and a report of what a caller may do.

## Starting your own use case

Until `cedar-osdc new` exists, copy `learn/hello` to
`usecases/<name>`, then in this order: replace the two Unity files
with your table and tags, or write them by hand in the same shape;
edit `facts.json` for your sample callers and records; edit the two
schema fragments for your principals and verbs; rewrite `usecase.py`;
run `build`; write the corpus cases before the policies; write the
policies; run `run-tests` until they pass; run `check-access` for each
caller and read the result as a governance decision.
