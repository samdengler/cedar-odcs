The guide

What you need to know about your own domain to fill in a use case, what each file in the folder is for, the three policy shapes the project has, and the command line. The learning path shows all of this running; this page is the reference.

1. Six questions about your domain

Every use case is a tool, the API behind it, and the rules that govern it. These questions decide what goes in the descriptor and the contract. Facts come from the credential and the tool input first; a lookup is added only for a gap the answers prove.

  1. Identity. What bearer token reaches the Gateway, and whom does its subject identify: a customer, an employee, or the agent itself? Which claims carry roles, and is there an actor claim for acting on behalf of someone? If customers have no identity, as with a reservation held by locator and last name, say so: the customer becomes presented facts, never a principal.
  2. Verbs. Which operations does the tool expose, and which are reads and which are writes? Writes are gated on the request leg before the call; reads are filtered on the response leg.
  3. Rules and their facts. For each rule, which facts decide it? Which are in the credential or the tool input already? Which live only in the record, like an owner or a holder's name? A rule that needs the record decides on the response leg for reads, and after a pre-fetch for writes.
  4. Data contract. What does the response contain, field by field, nested fields included, and what level does each carry? A field outside the contract is stripped, so the contract must be complete before onboarding.
  5. Writers. Which fields may a caller set, and which caller: the owner, a role, or nobody?
  6. Grants. Which roles hold which verbs, and which levels does each reader hold?

Identities, responses, and events are fixtures: data the engine or a handler reads as it would read the real thing. The one mock is the descriptor's fetch, which for a write that needs the record reads a saved response instead of calling the API, and is replaced by a real read at deployment.

3. From the catalog to the policies' inputs

4. The three policy shapes

Every policy in the project is one of these. Copy the one you need and change the names.

Ownership. The record names its owner, and the caller is the owner. From hello:

@id("owner-reads-own-note")
permit(
  principal,
  action == Action::"ReadNote",
  resource
) when {
  resource has owner &&
  resource.owner == principal
};

Possession. The caller presents facts, and the record confirms them. From reservations:

@id("read-by-possession")
permit(
  principal,
  action == Action::"ReadReservation",
  resource
) when {
  context has presented &&
  resource has recordLocator &&
  resource has holderLastName &&
  resource.recordLocator == context.presented.locator &&
  resource.holderLastName == context.presented.lastName
};

A role holding a verb, or a role holding levels. The caller is in a role, and the role grants the verb or the levels. From orders, the field form, with the acting-mode condition that turns the role off while acting for a customer:

@id("support-fields-on-any-order")
permit(
  principal in Role::"support",
  action == Action::"ReadOrderField",
  resource
) when {
  !(context has actingFor) &&
  context has field &&
  Contract::"Order".hasTag(context.field) &&
  ["public", "internal"].contains(Contract::"Order".getTag(context.field))
};

A field policy of any shape ends the same way: the field is looked up in the map by path, and the policy names the levels it grants, or the writer it requires. Nested fields are paths: contact.email, passengers[].seat.

Two habits beside the shapes. Guard every attribute read with has, so a record the store does not know fails closed instead of raising an error. And write a forbid for each invariant you rely on, under guardrails/, so the analysis holds it over every request; the proofs page says what that gives you.

5. Identity files

An identity file is a JSON object of claims, standing in for the JWT the Gateway has verified. It is named for who is calling. The projection reads:

ClaimMeaning
subthe principal, or, when act is present, the human acted for
act.subthe actor when the token was exchanged: the agent, typically
rolesthe subject's roles, added to the store's
client_id equal to suba workload token: the principal is an Agent

These are the claims the project assumes; the identity setup confirms them. Presented facts such as a locator and a last name are not claims: they come from the tool arguments the tool table names.

6. The command line

uv sync                                   # once, at the repository root
uv run cedar-odcs check DIR               # build, validate, run-tests, prove, in order
uv run cedar-odcs run-tests DIR           # the test cases, every case named
uv run cedar-odcs authorize DIR --principal ... --action ... --resource ...
uv run cedar-odcs dry-run DIR --caller C.json --tool NAME --arg k=v [--response FILE]
uv run cedar-odcs check-access DIR --caller C.json [--presented k=v] [--record FILE]
uv run cedar-odcs share DIR --case "text from a case description"
uv run cedar-odcs build DIR               # catalog to contract to Cedar
uv run cedar-odcs validate DIR            # the official cedar command if installed, else the binding
uv run cedar-odcs prove DIR               # needs Rust and cvc5; see analysis/README.md
uv run cedar-odcs prove                   # the history chain

run-tests, authorize, and validate do what the official cedar command's verbs of the same names do, on the same files. check, dry-run, and check-access are this project's: the four gates in order, one tool call through both legs without calling the tool, and a report of what an identity may do.

7. Starting your own use case

Until cedar-odcs new exists, copy usecases/hello to usecases/<name>, then in this order: replace the two Unity files under contract/unity/ with your table and tags, or write them by hand in the same shape; edit facts.json for your sample callers and records; edit the two schema fragments for your principals and verbs; rewrite usecase.py; run build; write the test cases before the policies; write the policies; run check until it is green; run check-access for each identity and read the result as a governance decision; then write a guardrail for each sentence you would put in a governance document.
