Iteration 2 gated the whole write; this iteration asks a second round on the request payload, one question per field the caller tries to set, and rejects the whole call if any field comes back Deny.

1. The problem

An owner who may update their order may still not set every field of it. Alice may change her shipping address; she must not change status (the fulfillment system's job), total (OWASP's own example scenario for this category is a client adding a price property to a request), or a field the contract never declared at all, like isAdmin. The attack of a client setting object properties it should not is API3's write half, named Mass Assignment in the 2019 edition[1].

Like iteration 2's object-level gate, this check cannot wait for the response: an applied write is done. The per-field round runs on the request payload, before the upstream call, completing the read/write pairing: iteration 3 asked per-field questions about the response, this iteration asks them about the request.

2. Scope of this iteration

Built: the field-writes folder in this project. The five policies from iterations 1 through 3 plus one write-field policy, a writers map alongside the classification map, a check_request gate that rejects a payload whole when any field is denied, eleven new corpus cases with all twenty-four prior cases carried, and thirteen properties proven in analysis/.

Not built: role-granted writes (a support agent updating internalNotes needs API5 first; see open questions), any reconciliation of full-object PUT payloads, Create and Delete verbs, ODCS parsing, and Gateway integration.

3. The payload round on the request leg

Two rounds now run before a write is forwarded. The object-level gate from iteration 2 answers whether this principal may update this order at all. Then, for each field in the payload, one more question:

{
  "principal": { "type": "User", "id": "alice" },
  "action":    { "type": "Action", "id": "UpdateOrderField" },
  "resource":  { "type": "Order", "id": "order-1001" },
  "context":   { "field": "total" },
  "decision":  "Deny"
}

The enforcement move is the inverse of the response leg's. A response with denied fields is stripped and forwarded; a write with any denied field is rejected whole, with the denied fields named. Forwarding the acceptable remainder would apply a request the caller never made.

4. The writers map

Which fields a caller may set is not derivable from the read classification. status is public to read and writable by nobody through this path; shippingAddress is confidential to read and is exactly what an owner should update. So writes get their own map, a second tag map beside the classification, whose values name the writer:

{ "uid": { "type": "Contract", "id": "Order/writers" },
  "tags": {
    "id":              "system",
    "status":          "system",
    "total":           "system",
    "shippingAddress": "owner",
    "cardLast4":       "system",
    "internalNotes":   "system",
    "fraudScore":      "system"
  } }

owner means the order's owner may set it; system means nobody may through this path, because the field belongs to upstream systems. The write-field policy is the same pattern as the read policies, looking the field up in this map:

@id("customer-updates-own-order-fields")
permit(
  principal,
  action == Action::"UpdateOrderField",
  resource
) when {
  resource has owner &&
  resource.owner == principal &&
  context has field &&
  Contract::"Order/writers".hasTag(context.field) &&
  Contract::"Order/writers".getTag(context.field) == "owner"
};

Both dimensions side by side:

FieldRead levelWriter
id, status, totalpublicsystem
shippingAddressconfidentialowner
cardLast4confidentialsystem
internalNotesinternalsystem
fraudScorerestrictedsystem

An undeclared field fails the hasTag guard, so mass assignment fails closed the same way undeclared reads do: isAdmin is denied not by a rule about isAdmin but by the absence of any entry granting it. And cardLast4 is system despite being about the customer's own card, because it is derived from the payment instrument; replacing a card is an action of its own, which belongs to the function-level iteration, not a field write.

5. The iteration, file by file

Everything from the first three iterations is recognizable; each file grew in one direction.

  • policies.cedar carries the five prior policies verbatim and appends P6, the write-field policy. There is no support policy for writes: the role grants no field writes, matching the object-level gate.
  • entities.json carries the prior facts and adds the Contract::"Order/writers" entity. Two tag maps now stand in for two columns of the same future data contract.
  • write_gate.py is the request-leg counterpart of field_filter.py. check_request(principal, resource, body) asks one question per payload field and rejects the whole call if any is denied: 
    denied = [
    name
    for name in body
    if not is_allowed(
        principal, 'Action::"UpdateOrderField"', resource, {"field": name}
    ).allowed
]
return RequestDecision(allowed=not denied, denied_fields=denied)
  • tests/bola.json, tests/bola-writes.json, and tests/field-reads.json are the corpora of iterations 1 through 3, byte for byte, the regression gate proving the appended policy changes no earlier decision.
  • tests/field-writes.json adds eleven UpdateOrderField cases: the owner's one allow, denies for every system field including the price manipulation case, mass assignment failing closed on isAdmin, API1 re-checked at write-field level, support and unknown principals, and the guessed order id.
  • test_corpus.py is the same runner, unchanged. test_gate.py pins the enforcement: a payload with one good and one denied field is rejected as a unit, the rejection names the denied fields, and a payload naming no field is rejected.

6. Growing by tests

The project's working loop (stated on the index page) held: the eleven cases were written first as the statement of the rule, then the one policy and one map entry set that make them pass. The corpus keeps the division of labor from iteration 3: corpus files pin decisions and stay engine-portable; test_gate.py pins what enforcement does with them, here rejection rather than stripping.

7. Proved as well as tested

This is the first iteration built after the analysis/ prover existed, so its invariants were proven at build time rather than retrofitted. Three new guardrails hold over every possible request, payload, and writers map:

  • Mass assignment fails closed. A write naming no field, or naming a field absent from the writers map, is never allowed, for every field name at once.
  • System fields are unwritable. Whoever asks, including the owner.
  • Writes require ownership. No role-granted write path exists at all, which is stronger than the read side, where support reaches public and internal fields of any order.

The four applicable guardrails from iterations 2 and 3 are carried and reproven against the grown policy set, the way the corpora are carried and rerun: a first taste of the provable-composition iteration. Findings and instructions are in analysis/README.md.

8. Running it

From the repository root, every iteration's tests run in one command:

uv run pytest -v

The iteration also runs standalone, and the proofs run from analysis/:

uv run --project field-writes pytest -v
cd analysis && cargo run

9. Decisions made in this iteration

A denied field rejects the whole payload, and the rejection names the fields. Iteration 2's reject-whole rule, now field-granular. The named fields make the rejection actionable for the caller and auditable for governance.

Writability is its own map. It cannot be derived from read levels, so it gets a second tag map with the same mechanism, the same fail-closed guard, and the same future source: one ODCS contract carrying both a classification column and a writability column.

Writer values name who may set the field: owner or system. No value for support exists yet, because the object-level gate already excludes the role from updates; a role-writable field would first need a role-granted object permit, which is API5's business.

cardLast4 is system. It is derived from the payment instrument. Changing cards is a verb with its own authorization, not a property assignment.

10. Open questions

  1. PATCH against PUT. The gate assumes the payload lists only the fields the caller intends to change. A client that echoes the whole object back, unchanged system fields included, is rejected here for fields it never meant to touch. Either tool registration requires PATCH semantics, or the gate diffs the payload against a pre-fetched current object. The choice belongs with the contract and Gateway iterations.
  2. Role-granted writes. Support plausibly should update internalNotes. That needs a role-granted object-level update permit first (API5), a writer value naming the role, and a knowing revision of the writes-require-ownership guardrail, whose diff would make the widening visible.
  3. What a rejection reveals, carried from iteration 2: naming denied fields helps legitimate callers and also tells an attacker which fields exist. The denial format decision covers both legs.

Glossary

TermMeaning
Mass assignmentThe write half of API3: a client setting object properties it should not, such as a price or a privilege flag. Defended here by the writers map and fail-closed denial.
Writers mapThe entity tags on Contract::"Order/writers": field name to writer. The second column the data contract will generate.
WriterWho may set a field: owner (the order's owner) or system (nobody through this path).
System fieldA field maintained by upstream systems, writable by no caller: status, total, fraudScore, and every derived value.
PATCH semanticsA write payload that lists only the fields being changed. The gate assumes it; full-object echoes are an open question.
