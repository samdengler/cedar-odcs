1. The problem

Fourteen iterations of design documents are the record of how the mechanism came to be. They are not how to learn it. A colleague with a different domain needs to see a decision within minutes, change something and watch a test fail, and know which of the pieces are theirs to fill in. Cedar already teaches Cedar, with a fixed reading order, a hands-on tutorial, and a playground; this project should teach only what it adds.

2. Scope of this iteration

Built: the learn directory: a path of three steps, the first a new use case of five fields and four policies, the other two exercises on the orders and reservations use cases; a guide built from the onboarding questions, with the three policy shapes in real Cedar and the command line reference; a page on how the proofs are used and what they do not cover, with the same assumptions written into the analysis README where an over-claim stood; and caller files, one per caller, for every use case. The root README leads with the path.

Not built: scaffolding a use case with cedar-osdc new, and building from a plain fields file (iteration 16). Until then the guide says to copy the hello use case.

3. Three steps, after Cedar's own

Each step names the Cedar pages it assumes, from the docs' own first-time sequence, gives the commands, and ends with a change that makes a test fail.

The second and third steps are exercises on the real use cases rather than reduced copies, so what a learner runs is what the tests and the proofs run. The pages are Markdown, because a colleague will read them where the clone lives, on GitHub or in an editor, and the design documents stay the deep reference behind each idea.

4. The hello use case

A note has an owner; a reviewer may read any note; five fields carry three levels. Four policies, nine corpus cases, two callers, one tool, and the same build pipeline as the real use cases, from a Unity Catalog table fixture through an ODCS document to the generated maps. Nothing is simplified in kind, only in size: the first thing a learner rebuilds is the same artifact a deployment would.

$ uv run cedar-osdc check-access learn/hello --caller learn/hello/callers/ada.json

5. The guide and the proofs page

The guide restates the README's six onboarding questions as what to know about a domain before filling in a use case, maps each answer to the file it lands in, shows the three policy shapes the project has, ownership, possession, and a role holding a verb or levels, each quoted verbatim from a use case, and ends with the command line and a map from each idea to the design document that explains it.

The proofs page answers the question a reader asked of this project and its colleague will ask too: how are the proofs used, and what do they not cover. The second half is the part that was missing everywhere: the proofs are about policies under a schema, not the code that builds requests; a guardrail can be vacuous; a declared revision makes a change visible rather than right; and the verified part is the compiler. The analysis README said the proofs were trustworthy end to end, which the critical review called an over-claim; it now says what a green run does and does not establish, in a section of its own.

6. Caller files

The command line took a token file, one JSON object of claims. The word misled: a reader of an agent project hears "token" and thinks of what a language model counts. The file is named for who is calling, and it is now a caller file, --caller callers/ada.json, with one per caller shipped in every use case. The word token remains where it means the JWT the Gateway verifies, which the caller file stands in for.

7. The iteration, file by file

  • learn/README.md: the path, the Cedar reading it assumes, and what is not there yet.
  • learn/hello/: the use case, with its own README.md as step 1, and tests that run with everything else.
  • learn/roles.md, learn/possession.md: steps 2 and 3.
  • learn/guide.md, learn/proofs.md.
  • analysis/README.md: the over-claim replaced and "What the proofs assume" added.
  • core/cli.py: --token becomes --caller; callers/ in each use case.
  • README.md: leads with the path and the command line; the history follows.

9. Decisions made in this iteration

Teach only what Cedar does not. Each step names the Cedar pages it assumes and starts after them.

Exercises on the real use cases, not reduced copies. Only the hello step is new content.

Markdown for the path, the design documents for depth.

Every step ends by breaking something. The loop is the method.

A caller file, not a token file.

10. Open questions

  2. Scaffolding and a plain fields file, so a learner's own use case does not begin as a copy: iteration 16.
