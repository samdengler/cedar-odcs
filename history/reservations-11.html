Cedar authorization for MCP tools, iteration 11: reservations by locator and last name

A second use case to pressure test the mechanism. A reservation is held by whoever presents its record locator and the holder's last name; there is no customer identity beyond that pair. The customer is never a principal, the check runs on the response leg, the record is nested, and the mechanism moves into a core that names no use case.

1. The problem

Ten iterations built governance for orders, and every rule about who may reach an order compared an identity to its owner. The next questions on that work, how the token's subject maps to an owner and what bounds an employee acting for a customer, are questions about identity. Before answering them for orders, the mechanism is tried on a use case with no customer identity at all.

A reservation is identified by a record locator and the last name on the reservation. Whoever presents that pair holds the reservation; that is how the airline works, on the phone and on the web. A customer has no login the rules may rely on and no loyalty identifier they may compare. The reservation carries several passengers, and the pair names one of them, the holder. The record itself is nested: passengers and flight segments are lists, contact details an object.

Three things follow, each a blind spot of the order model. The customer cannot be a Cedar principal. The check cannot run before the record has been fetched. And the field round has to name leaves inside lists.

2. Scope of this iteration

Built: the core directory, the mechanism extracted from iterations 6 through 10 with no use case named in it; usecases/orders, iteration 9's policies and iteration 7's contract running on core with every corpus and every Gateway fixture carried, at parity; and usecases/reservations: a Unity Catalog fixture with struct and array columns, an ODCS document with nested properties, path-keyed tag maps, three possession policies, fifteen corpus cases, five Gateway fixtures, and six guardrails proven. The reservations chain joins the proofs beside the orders chain.

Not built: writes by possession and the pre-fetch they need (iteration 12), the specialist's view, the list verb, and the agent as a party of its own (iteration 13), the mask across requests, and any lockout against guessed last names.

3. Possession, presented in context

The pair arrives in the tool input on every call. The handler copies it into the request context as presented, and the policies read it there. The record's locator and holder last name are attributes of the resource entity, and the read policy is an equality on both:

@id("read-by-possession")
permit(
  principal,
  action == Action::"ReadReservation",
  resource
) when {
  context has presented &&
  resource has recordLocator &&
  resource has holderLastName &&
  resource.recordLocator == context.presented.locator &&
  resource.holderLastName == context.presented.lastName
};

The principal is unconstrained. Whoever holds the token, the agent in a customer conversation or a specialist, gets the same answer for the same pair; the credential is the pair, and the token says only who presented it. Here is the case that pins the holder's read, and beside it the one that pins a co-traveler's:

{
  "description": "the record is readable when locator and holder last name are the presented ones",
  "principal": { "type": "User", "id": "reservations-assistant" },
  "action":    { "type": "Action", "id": "ReadReservation" },
  "resource":  { "type": "Reservation", "id": "ABC123" },
  "context":   { "presented": { "locator": "ABC123", "lastName": "SMITH" } },
  "decision":  "Allow",
  "reason":    ["policy1"]
}
{
  "description": "a co-traveler's last name is not the holder's: the pair names one person",
  "principal": { "type": "User", "id": "reservations-assistant" },
  "action":    { "type": "Action", "id": "ReadReservation" },
  "resource":  { "type": "Reservation", "id": "ABC123" },
  "context":   { "presented": { "locator": "ABC123", "lastName": "PATEL" } },
  "decision":  "Deny"
}

The locator is part of the credential, so a pair valid for one reservation reads nothing of another, and the corpus pins that too. Last names are compared upper-cased: the handler upper-cases what was presented, and the contract states the record holds the holder's name that way.

4. Two legs, one credential

Nothing about the pair can be verified before the record exists. The request leg therefore asks a different question from the response leg, and the two get different verbs. LookupReservation is the request leg's: permitted to anyone presenting a pair, refused for a locator alone. ReadReservation is the response leg's: the policy above, evaluated against the entity built from the payload, followed by the field round. A mismatch leaves the response empty.

This is the placement iteration 1 named for ownership checks that need the object's attributes, arrived at because there is no other. It also answers, for this use case, the question the critical review put first about orders: where the request leg gets the object's facts. For reads it does not need them.

5. Nested records by path

The field round from iteration 3 named a field. Here a leaf sits inside a list of passengers, and its classification must apply to every passenger. The maps are keyed by path: contact.email for a leaf of an object, passengers[].seat for a leaf of every element of a list. The generated classification map:

{ "uid": { "type": "Contract", "id": "Reservation" },
  "tags": {
    "recordLocator": "public",
    "holderLastName": "public",
    "status": "public",
    "passengers[].firstName": "public",
    "passengers[].lastName": "public",
    "passengers[].dateOfBirth": "confidential",
    "passengers[].seat": "public",
    "passengers[].passportNumber": "restricted",
    "passengers[].specialServiceRequests": "restricted",
    "segments[].flightNumber": "public",
    "segments[].origin": "public",
    "segments[].destination": "public",
    "segments[].departure": "public",
    "contact.email": "confidential",
    "contact.phone": "confidential",
    "fare": "confidential",
    "paymentLast4": "confidential",
    "remarks": "internal"
  } }

Containers have no level of their own; only leaves do. The field round walks the payload and asks one question per distinct path, so a record with two passengers costs one decision for passengers[].seat, applied to both. That is iteration 1's mask, arrived at because paths made it natural. A leaf whose path is in no map is stripped, an object that loses every leaf goes with them, and a list whose elements all emptied goes too.

The levels come from Unity Catalog, which attaches tags to columns and not to the fields inside a struct. The path travels in the tag key instead: classification__passport_number on the passengers column is the level of passengers[].passportNumber, and the column's own classification tag is the level of every leaf under it that has no key of its own. The contract build reads the column's Spark type from the catalog's type_json and writes nested ODCS properties, which the standard supports.

6. Core and the use cases

The mechanism now lives in core, extracted from iterations 6 through 10 only as this use case demanded: the corpus runner, the claims projection, the two legs of enforcement, the Gateway handlers, and the contract build. A use case is a directory with policies, facts, a contract's sources, corpora, fixtures, and a descriptor:

USE_CASE = UseCase(
    name="reservations",
    root=ROOT,
    resource_type="Reservation",
    attributes={"recordLocator": "String", "holderLastName": "String"},
    id_field="recordLocator",
    read_action='Action::"ReadReservation"',
    read_field_action='Action::"ReadReservationField"',
    field_actions={},
    tools=TOOLS,
)

The descriptor says what the mechanism cannot know: the entity type a payload row becomes, which of its fields are attributes and of what type, the verbs for the two rounds of each leg, and the tool table. Everything else is core's. The test of the split is the orders use case: iteration 9's policies and iteration 7's contract sources, run through core, pass every corpus and every Gateway fixture the numbered iterations pinned. The ten iteration directories stay untouched as the narrative.

The writeup of what core had to change to admit reservations is deferred to the end of the use case, once iterations 12 and 13 have made their demands too.

8. Growing by tests

The fifteen cases were written before the policies, and the Gateway fixtures before the handlers. Two things the tests decided. The corpus case for an unknown record made the read policy guard both attributes, so a record the store does not know fails closed with no evaluation error, where iteration 1's unguarded policy still errors. And the fixture with a co-traveler's name fixed what the response leg returns on a mismatch: an empty object, because the call succeeded upstream and nothing of the record may be shown.

The orders parity tests found the two places core diverged from iteration 10 in extraction: the rejection message named the full action reference instead of the verb, and a nested list whose elements had all emptied was kept as an empty list.

9. Proved as well as tested

Six guardrails hold over every request and every record:

  • A lookup requires a pair. A locator alone is never attempted.
  • A read requires a pair. True while possession is the only path; iteration 13's specialist view will retire it knowingly.
  • Possession names the record. A pair reaches only the record whose locator and holder it names.
  • Undeclared paths fail closed, nested ones included.
  • Restricted leaves are unreadable: passport numbers and medical requests.
  • Possession reads the customer's levels only. The specialist's remarks are never revealed to the pair.

The analysis runner now knows two chains. The orders chain gained the use case on core as its final member, proven to preserve iteration 9's decisions under the schema core's build wrote; the reservations chain begins here. Each chain's guardrails are given their status against that chain's final set. Findings and instructions are in analysis/README.md.

10. Running it

From the repository root, every iteration's and every use case's tests run in one command, and every test and proof together in another:

uv run pytest -v
./check.sh

The build for one use case:

uv run python usecases/reservations/build.py

11. Decisions made in this iteration

The customer is never a principal. Possession is presented in context and checked against the record. The principal is whoever holds the token.

The request leg asks a different verb from the response leg. The lookup is permitted on the pair alone; the read is decided on the record. Two verbs make the two questions visible in the corpus and the proofs.

Maps are keyed by path, and containers have no level. A nested leaf's level applies to every element. The mask is one decision per distinct path.

Nested levels travel in Unity Catalog tag keys. The catalog is still the source of truth; the convention is stated in the build's docstring and can be replaced by a governed tag scheme.

A mismatch returns an empty record. The call succeeded upstream; nothing of the record is shown; no error confirms or denies that the locator exists.

Core is extracted, never designed ahead. Each piece moved because reservations needed it, and orders holds parity on every move.

12. Open questions

  1. Lockout. A pair is guessable, and the gateway cannot count attempts on its own. Where guessed last names are stopped, upstream or in the Gateway, is a deployment decision the rules cannot make.
  2. The empty record on a mismatch. Returning nothing reveals nothing about the locator, but an agent cannot tell a wrong name from an empty reservation. Whether a distinct signal is worth the leak is a product question.
  3. Writes by possession, and the pre-fetch a write needs before it can be forwarded: iteration 12.
  4. The specialist's view, the list verb, and the agent as a principal of its own type: iteration 13.
  5. Struct fields the catalog cannot tag. The path-in-the-key convention works and is ours; Databricks may add nested tags, or governed tags may not accept the scoped keys.
