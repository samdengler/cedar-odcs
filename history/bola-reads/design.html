Cedar authorization for MCP tools, iteration 1: broken object level authorization (BOLA)

A standalone Cedar policy engine setup that answers one question, "may this principal read this object", as the first step toward data governance for agent tool calls.

1. The problem

An agent running on AgentCore Runtime calls an upstream API through an MCP tool registered in AgentCore Gateway. The tool authenticates with a service credential, so the API sees a trusted caller and returns whatever is asked for. If the agent requests order 2002 while acting for the customer who owns order 1001, the API returns order 2002 anyway. The API layer has no governance to stop it, and fixing the APIs themselves is not an option in the near term.

The governance therefore has to live in the agent stack, between the tool call and the upstream API. The threats to cover, in OWASP API Security Top 10 terms:

  • API1, Broken Object Level Authorization (BOLA)[1]. Reading an object that belongs to someone else by swapping an id.
  • API3, Broken Object Property Level Authorization[2]. Receiving fields inside an allowed object that this caller should not see, such as a card number.
  • API5, Broken Function Level Authorization (BFLA)[3]. Calling an action reserved for another role, such as issuing a refund.

The plan is to express the rules in Cedar[4], eventually derive them from Open Data Contract Standard documents[5], and enforce them at the Gateway. This document covers only the first iteration: BOLA, standalone, in Python, with tests.

2. Scope of this iteration

Built: the bola-reads folder in this project. Two Cedar policies, a set of entity facts, a Python wrapper of about thirty lines, and six pytest tests, all passing. It runs on a laptop with no AWS dependency.

Not built: field filtering (API3), function level checks (API5), any parsing of ODCS documents, and any integration with AgentCore Gateway or Runtime. Sections that mention those describe intent, not working code.

3. Where Cedar sits in the eventual stack

Cedar is a policy engine, a library that evaluates rules. It does not intercept anything on its own. Something in the request path has to call it and enforce its decision. In authorization jargon the engine is the PDP (policy decision point) and the code that calls it is the PEP (policy enforcement point). The natural PEP in this stack is an AgentCore Gateway interceptor, which can inspect and modify tool calls and responses[6].

The interceptor runs on both legs of the call. On the request leg it can reject a call outright, which covers function level rules (API5) and any object level rule whose facts are known up front. On the response leg it sees the fetched data, which is where the rest of the governance happens: ownership checks that need the object's attributes (API1), and stripping fields or rows the caller may not see (API3).

Nothing about this iteration depends on this placement being final. The Python wrapper takes the same inputs an interceptor would and returns the same answer: a principal, an action, and a resource in; allow or deny out.

4. Cedar concepts used in this iteration

The code sample rests on five concepts.

Request. Every question to Cedar has the same four parts, called PARC: a principal (who), an action (doing what), a resource (to what), and a context (extra facts about this call, empty in this iteration). Example: may User::"alice" perform Action::"ReadOrder" on Order::"order-1001"?

Policy. A rule that permits (or forbids) some set of requests. The core BOLA policy in this iteration is three lines:

permit(principal, action == Action::"ReadOrder", resource)
when { resource.owner == principal };

Entities. The facts the policies refer to: which users exist, which orders exist, who owns each order, who is in which role. This iteration keeps them in entities.json. This is the piece that will later come from data contracts and real systems.

Default deny. If no permit policy matches, the answer is Deny. There is no rule saying "deny access to other people's orders"; that outcome falls out of the absence of a permit. Default deny is most of the BOLA defense by itself.

Decision with diagnostics. The engine returns Allow or Deny plus the list of policies that determined the outcome. A deny with an empty list means default deny. This is useful in tests and later in audit logs.

Cedar also has a schema mechanism that validates policies against declared entity types. This iteration skips it to keep the moving parts down; it enters in a later iteration alongside ODCS, since a data contract is a natural source for a schema.

5. The BOLA iteration, file by file

Four files in bola-reads/, readable in one sitting.

  • policies.cedar holds two policies: a customer may read an order whose owner attribute equals the principal, and anyone in Role::"support" may read any order. That second policy exists to show role membership, which is how BFLA rules will look later.
  • entities.json holds the facts: three users (alice, bob, and carol the support agent), one role, and two orders with owners. Carol's membership in the support role is expressed by listing the role among her parents, Cedar's group mechanism.
  • authorizer.py loads both files and exposes one function, is_allowed(principal, action, resource), wrapping the cedarpy bindings[7]. It does the same job a Gateway interceptor will do: load rules, answer questions.
  • tests/bola.json is the interesting file. The test cases are data: each entry is one authorization question phrased as either a legitimate request or an attack (alice reads her own order, alice swaps the id to bob's order, carol reads anything, an unknown principal or a guessed order id), with the expected decision, the policies expected to determine it, and any expected evaluation errors. The file follows the format of the Cedar project's own integration-test corpus[12], which the Rust and Java engines already run in CI.
  • test_corpus.py is a thin pytest runner that feeds every case in tests/ to the engine. Because the cases are engine-independent data in an established format, a future Rust enforcement build runs the same JSON files with a Rust runner; the governance rules are defined once.

6. Running it

The project uses uv[8]; dependencies are declared in pyproject.toml and resolved on first run. From the repository root, every iteration's tests run in one command:

uv run pytest -v

The iteration also runs standalone:

uv run --project bola-reads pytest -v

7. Direction settled in review

The first review resolved the original three open questions.

Response schemas come from tool authors at registration. Registering an MCP tool requires a schema for the response, with a classification on each field. That artifact is a data contract, and ODCS already defines per-field classification for it[5], so tool registration and contract publication can be the same act. The Cedar schema and the field sensitivity map are compiled from the contract. Invariant to enforce: fields present in a response but absent from the contract are stripped, so schema drift fails closed instead of leaking data.

Requests carry an actor and an acting-for party. The system implements on behalf of (OBO) access. Three modes exist: a customer interacting directly, an employee interacting directly, and an employee acting for a customer. The principal stays the actual actor; the context carries whom they act for. Employee-only permits require direct mode, and ownership permits evaluate against the acting-for party, so an employee acting for a customer holds roughly the intersection of the employee's and the customer's access. This follows existing standards rather than inventing a model: OAuth 2.0 Token Exchange[10] carries the actor in an act claim while the subject remains the acted-for party, and the Cedar context is a direct projection of those claims. The intersection semantics match the widely deployed Microsoft Entra on-behalf-of flow[11]. This requirement is stated ahead of the facts: on behalf of exists in the identity setup but is new, and today's claims may not carry everything these rules check. The OBO iteration's corpus makes the requirement testable, because each case names the claims its context needs. Comparing today's tokens against those cases is the claims gap analysis, and any shortfall becomes a change request to the identity setup rather than a silent redesign.

The interceptor strips, it never rejects. There is no case where a whole response is refused. Undeclared or denied fields are removed and the removal is logged; the remainder is returned.

Enforcement lives in a Rust Lambda extension. Interceptors are Lambda functions, and governance must hold even when tools teams implement their own response logic. A Runtime API proxy extension wraps the Lambda Runtime API endpoint, sees the invocation and the function's response payload, and rewrites the response before Lambda returns it, independent of the function code[9]. Cedar is Rust-native, so the engine runs in-process in the extension. Policies are compiled from the contract at publish time.

Per-request cost is bounded by mask caching. Post-fetch enforcement has to touch every response; that cost is inherent until governance can be pushed down into queries. But field permits depend on role, mode, and classification, not on row values, so the field mask for a given (principal mode, contract version) pair is computed once, cached, and applied as a plain JSON transform. Only ownership and row checks, which depend on the data, run Cedar per request.

8. Open questions

  1. Identity propagation, now a fact-finding item: what the bearer token carries (issuer, what the subject identifies, roles, tenant or account scoping, an act claim for on behalf of), what of it the Gateway delivers to policy evaluation and to interceptors, and whether OAuth token exchange is available in the identity setup. This inventory gates every design that needs facts at decision time: a fact already in the token or the tool input needs no machinery, and lookups or entity stores enter only for gaps the inventory proves. The same questions repeat for each new use case; the README records them as the onboarding questions.
  2. How stripped-field removals are surfaced to tool authors, so schema drift gets fixed rather than silently masked forever.
  3. Measured numbers for the response-path overhead on realistic payloads, once the mask caching exists to measure against.

Glossary

TermMeaning
BOLABroken object level authorization, OWASP API1. Reading an object that belongs to someone else by swapping an id.
PDPPolicy decision point. The engine that evaluates rules and returns Allow or Deny. Cedar plays this role.
PEPPolicy enforcement point. The code in the request path that calls the PDP and enforces its answer. The Gateway interceptor plays this role.
PARCPrincipal, action, resource, context. The four parts of every Cedar request.
ODCSOpen Data Contract Standard. A YAML format describing a dataset's schema, quality, and terms of use.
OBOOn behalf of. A request made by one party acting for another, such as an employee acting for a customer.
EntityA Cedar fact about a user, role, or object, including its attributes and group memberships.
