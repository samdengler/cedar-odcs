Cedar authorization for MCP tools, iteration 9: row filtering for list endpoints

A list call returns many orders. The verb is granted to everyone, because it decides nothing: each row is authorized with the question iteration 1 asked of a single order, and each surviving row is reduced to the fields the caller may read. The rows themselves become the entities.

1. The problem

Every case so far names one order. A tool that lists orders returns many, and the upstream API, authenticated with a service credential, returns all of them: alice's, bob's, everyone's. That is broken object level authorization[1] over a collection, and the request leg cannot prevent it, because the rows do not exist until the API has answered. The defense is the response leg's, like field filtering was in iteration 3.

Two things are new. The list verb needs a decision of its own, and the answer is that it needs almost none. And for the first time the objects being decided on are not in entities.json: they are in the payload, which is where the enforcement point will always find them.

2. Scope of this iteration

Built: the row-filtering folder in this project. Iteration 6's twelve policies plus one list verb, a filter_rows wrapper that asks ReadOrder per row and the per-field round per surviving row, resource entities built from the rows, six new corpus cases with all sixty-nine prior cases carried, and twenty-five properties proven in analysis/, with one guardrail revised to name the order verbs.

Not built: pushing the row condition down into the upstream query, pagination and cursors, list verbs for other collections, and Gateway integration. The entities are iteration 7's build output, unchanged.

3. Rows are authorized one by one

The list verb is held by every principal, in either mode:

@id("anyone-lists-orders")
permit(
  principal,
  action == Action::"ListOrders",
  resource == Collection::"orders"
);

That reads as a wide grant. Listing decides nothing about what comes back. Dave in finance may call the list and receives no rows, because the finance role grants no read and the rows are decided by ReadOrder. The forbid from iteration 6 still applies: bob claiming to act for alice is refused the list call, and the corpus pins policy11 as the reason.

On the response leg, the wrapper asks per row what iteration 1 asked of one order, drops the rows that come back Deny, and then runs iteration 3's per-field round on each row that stays:

What each caller receives from the same three-row response, as test_rows.py pins it:

CallerRowsFields on each row
alice, direct1001 and 3003, her ownpublic and confidential
carol (support), directall threepublic and internal
dave (finance), directnone
carol acting for alice1001 and 3003, alice'spublic and confidential, as for alice

4. Entities from the payload

The ownership policies read resource.owner. In every earlier iteration the order entities and their owners sat in entities.json, a stand-in for a store the enforcement point does not have. On the response leg the store is unnecessary: the row carries the owner. The wrapper builds the resource entity from the row and asks about that:

ATTRIBUTES = {"owner": "User"}

def entity_from_row(row: dict) -> dict:
    attrs = {
        name: {"__entity": {"type": entity_type, "id": row[name]}}
        for name, entity_type in ATTRIBUTES.items()
        if name in row
    }
    return {"uid": {"type": "Order", "id": row["id"]}, "attrs": attrs, "parents": []}

Which payload field becomes an attribute, and of what type, is what iteration 7's contract says: the customer_id column carries the tag cedar_entity_type: User, the build wrote entity Order { owner: User }, and ATTRIBUTES is that declaration. Every other field stays a field, looked up in the tag maps by the field policies and never made an attribute.

A row is the fact about the order it describes, so it replaces any stored entity of the same id, and an order no store has ever heard of is decided the same way. A row with no usable id (absent, not a string, or holding characters an entity reference could misread) cannot be an entity and is dropped before any question is asked. A row with no owner is decided without ownership: the unguarded ownership policy from iteration 1 raises an evaluation error on it, which is a Deny, so a customer loses the row, while support, whose read policy needs no owner, keeps it with support's fields. Every removal is reported with the row's position, its id when it had one, and the reason.

5. The iteration, file by file

  • policies.cedar carries iteration 6's twelve policies verbatim and appends P13, the list verb.
  • entities.json is iteration 7's build output, unchanged. The collection entity is not in it: the permit names Collection::"orders" by id and needs no facts about it.
  • row_filter.py holds filter_rows(principal, rows, context): the row round with entities built from the rows, then the field round, returning the surviving rows, the rows dropped with position, id, and reason, and the fields stripped per row position.
  • tests/bola.json through tests/contract.json are carried byte for byte. tests/row-filtering.json adds six cases for the list verb: each role, the acting mode, the forbid, and another collection.
  • test_corpus.py is the same runner, unchanged. test_rows.py pins the response leg: the rows and fields each caller and mode receives, an order no store knows decided from its row, the ownerless row lost by a customer and kept by support, and the drop of a row with no usable id.

6. Growing by tests

The corpus cases came first and were brief: the verb is one permit. The response-leg tests were the substance. A filter that asked ReadOrder against entities.json would fail the test for an order the store never heard of, which is the iteration's claim: at the Gateway there is no store, and the row is the fact. The fail-closed tests came from asking what the wrapper should do with a row it cannot place. The ownerless row has no single answer: iteration 1's unguarded ownership policy errors on it, so a customer loses it, and support's read policy never looks at the owner, so support keeps it; the test pins both.

7. Proved as well as tested

The new permit never errors, and the twelve carried guardrails are reproven against the thirteen-policy set. One needed revising. Iteration 6's guardrail that acting mode is bounded by ownership was written over every action, and the list call is the one verb with no order to own; against the new set it forbade every list call made while acting, which the corpus allows. The revised guardrail names the six order verbs, and the composition run marks the old one revised and proves the new one. The preservation proof shows the six order actions decide as in iteration 7. Findings and instructions are in analysis/README.md.

8. Running it

From the repository root, every iteration's tests run in one command, and every test and proof together in another:

uv run pytest -v
./check.sh

The iteration also runs standalone:

uv run --project row-filtering pytest -v

9. Decisions made in this iteration

Listing is a verb everyone holds; rows are the authorization. A list permit scoped to roles would have to restate who may read what, which the row round already knows. Granting the verb to everyone keeps one source for the read rule.

Resource entities come from the payload. The response leg has the data, so no store is consulted for the objects being decided. This is the design the interceptor needs; the corpus keeps its stored orders because a corpus case has no payload.

The contract says which field is an attribute. The entity reference tag from iteration 7 is the only source of ATTRIBUTES. No field becomes an attribute by convention.

Rows the wrapper cannot place are dropped and reported. They fail closed, as undeclared fields do.

10. Open questions

  1. Pushing the row condition down. Filtering after the fetch costs a fetch of every row. Cedar's partial evaluation can reduce the read policies for a known principal to a condition on the unknown row, which is a query predicate on owner: the same idea as Unity Catalog's row filters, applied at the API. That moves governance into the query and is the only path to lists that scale; it needs the upstream API to accept a filter.
  2. Per-row cost. Iteration 1's review bounded the field round by caching the mask per caller and contract version. The row round asks one ReadOrder per row, whose only variable is the owner, so the same caching applies: one decision per distinct owner in the page.
  3. Pagination. A page whose rows were all dropped is an empty page the client cannot distinguish from the end of the list. Whether the interceptor fetches the next page itself or returns a cursor is a Gateway question.
  4. Collections other than orders, and what the list verb's resource should be when a tool lists a nested collection, such as the shipments of one order.
