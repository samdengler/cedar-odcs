Cedar authorization for MCP tools, iteration 10: enforcement in Gateway interceptors

The wrappers of iterations 1 through 9 become two Lambda handlers, one per Gateway interception point, driven by the exact events AgentCore Gateway documents. The policies, the entities, and the decisions are the ones already tested and proven; what is new is the last step from a Gateway event to a Gateway result.

1. The problem

Iteration 1 placed the enforcement point in the AgentCore Gateway, between the tool call and the upstream API, and then replaced it with a Python function so the Cedar part could be learned in isolation[1]. Nine iterations later the function has grown into a request leg (the verb round and the payload round) and a response leg (the field round and the row round), each pinned by a corpus and proven in analysis/. This iteration puts them back where they were always going: Gateway interceptors[2].

The Gateway invokes a request interceptor before it calls the target and a response interceptor before it answers the agent. Each is a Lambda function that receives the JSON-RPC message in flight and returns a transformed one, and the request interceptor can return a response instead, which the Gateway sends without calling the target. Those are exactly the two moves the iterations built: reject on the request leg, strip on the response leg.

2. Scope of this iteration

Built: the gateway folder in this project. Two handlers, request_handler and response_handler, in the interceptor event and result formats the Gateway documents for MCP targets; a tool table mapping MCP tool names to verbs and resources; the bearer token decoded from the forwarded header and projected as in iteration 6; eleven fixture events in those exact shapes; and thirteen tests driving the handlers with them. The policies are iteration 9's and the entities are iteration 7's build output, byte for byte, and a test says so.

Not built: deployment to an AWS account (a later step), the mask cache from iteration 1's review, streaming responses, and the Rust build. Nothing new is proven, because no policy changed.

3. The two interception points

The request interceptor receives the JSON-RPC message the agent sent, and, when the interceptor is configured with passRequestHeaders, the request headers including the bearer token[3]. Here is one fixture event, the shape the documentation gives, with the token shortened:

{
  "interceptorInputVersion": "1.0",
  "mcp": {
    "rawGatewayRequest": { "body": "..." },
    "gatewayRequest": {
      "path": "/mcp",
      "httpMethod": "POST",
      "headers": {
        "Accept": "application/json",
        "Authorization": "Bearer eyJhbGciOi...",
        "Mcp-Session-Id": "session-1",
        "User-Agent": "agent/1.0"
      },
      "body": {
        "jsonrpc": "2.0",
        "id": 2,
        "method": "tools/call",
        "params": { "name": "orders___refund_order", "arguments": { "orderId": "order-1001" } }
      }
    }
  }
}

The response interceptor receives the same request plus the target's response, gatewayResponse with its status, headers, and JSON-RPC body. Nothing arrives pre-parsed: the interceptor decodes the token itself, and the token it decodes is the one the Gateway's authorizer validated moments before, read from the request the Gateway forwarded and from nowhere else. Signature, issuer, audience, and expiry are the authorizer's job; the handler reads the payload.

4. The request leg handler

The handler names the verb and the resource from the tool name and its arguments, and the rest is iteration 5's check_call asked with a token:

TOOLS = {
    "orders___get_order":    {"action": "ReadOrder",   "id": "orderId", "returns": "object"},
    "orders___update_order": {"action": "UpdateOrder", "id": "orderId", "payload": "changes"},
    "orders___cancel_order": {"action": "CancelOrder", "id": "orderId"},
    "orders___refund_order": {"action": "RefundOrder", "id": "orderId"},
    "orders___list_orders":  {"action": "ListOrders",  "collection": "orders", "returns": "list"},
}

A tool the table does not name is rejected: an ungoverned tool is a gap, and the request leg fails closed on it the way the field round fails closed on an undeclared field. A method other than tools/call, such as tools/list, passes through untouched. An allowed call is returned as a transformedGatewayRequest with the same body. A denied one becomes a response the Gateway sends instead of calling the target, the short-circuit the documentation describes, carrying a JSON-RPC error so the agent sees a refused call and not a broken transport:

{
  "interceptorOutputVersion": "1.0",
  "mcp": {
    "transformedGatewayResponse": {
      "statusCode": 403,
      "body": {
        "jsonrpc": "2.0",
        "id": 2,
        "error": { "code": -32000, "message": "RefundOrder is not permitted for this caller" }
      }
    }
  }
}

That is alice asking to refund her own order, iteration 5's first BFLA case, as a Gateway result. A denied field in an update names the fields, as iteration 4 decided: carol acting for alice, changing the shipping address and the total, is refused with fields not permitted: total.

5. The response leg handler

The response interceptor can rewrite the result body[3], which is all the response leg ever needed. The handler finds the tool's payload in the MCP result, in structuredContent when the tool provides it and otherwise in the JSON text of the first text content item[4], runs iteration 9's filter_rows for a list tool or the one-row equivalent for an object tool, and writes the filtered payload back into both places so an agent reading either sees the same thing. The status and headers pass through; the removals go to the log.

The three response fixtures are iterations 3, 6, and 9 as Gateway events: alice's order comes back to her with the public and confidential fields; bob's order comes back to carol with the public and internal fields; and the full list comes back to carol acting for alice as alice's two rows with alice's fields, and to dave in finance as an empty list.

6. Where AgentCore Policy fits

The Gateway also has a native policy engine, AgentCore Policy, which evaluates Cedar policies against every tool call before the target is reached[5]. Its entity model is fixed: the principal is an AgentCore::OAuthUser built from the token's subject, with the other claims as tags on it; the action is the tool name; the resource is the gateway; and the context exposes the tool's input arguments. It evaluates on the request leg only, and it loads no entity data of its own.

Measured against the rounds this project built, that covers exactly one: the verb round for rules whose facts are in the token and the tool input. Whether a caller with the finance role may call the refund tool is such a rule, and so is the on behalf of forbid, if the actor claim appears as a tag. Ownership needs the order's owner, which is in no token; the field rounds need the tag maps, which are entities; and the response leg is outside the engine's reach. So the interceptors stay the enforcement point, and AgentCore Policy is a second, independent check on the verb rules, in LOG_ONLY mode first. The policies for it would be generated from the same corpus, in its entity model; that is a small follow-up once the claims table from iteration 6 is confirmed, because the tag names are the claim names.

7. The Lambda extension decision, revisited

Iteration 1's review placed enforcement in a Rust Lambda extension, a Runtime API proxy that rewrites a function's response independent of its code[6], so that governance would hold even when tool teams implement their own response logic. That concern assumed the interceptor logic would live in Lambdas the tool teams own. Gateway interceptors are Gateway configuration: one Lambda per interception point, attached to the gateway, run for every tool call through it whatever the target is[2]. The governance holds because the interceptor is ours, and a proxy around it would wrap our own code. The extension is set aside.

Rust remains a reasonable build for the interceptor itself. Cedar is Rust-native, the handlers here reach it through Python bindings to the same engine, and the corpus is engine-independent by design. That is a cost question for after deployment, measured rather than assumed, as the review said of the response-path overhead.

8. The iteration, file by file

  • interceptor.py holds the two handlers, the tool table, and the Gateway output formats: pass-through, short-circuit rejection, and transformed response.
  • enforce.py holds check_call, filter_fields, filter_rows, and filter_object: the wrappers of iterations 5, 3, and 9, asked with a token's projection. Entities for rows come from the payload, as in iteration 9.
  • claims.py is iteration 6's projection plus claims_of, which decodes the bearer token the Gateway forwarded.
  • policies.cedar and entities.json are iteration 9's policies and iteration 7's build output, byte for byte.
  • events/*.json are eleven Gateway events in the documented shapes, seven for the request leg and four for the response leg, with tokens encoded from iteration 6's payloads.
  • tests/*.json are every prior corpus, carried. test_interceptor.py drives the handlers with the events and pins the results, and pins that the policies and entities are the proven ones.

9. Growing by tests

The events were written first, from the documentation, and the tests said what each should produce; the handlers were written to them. Two things came out of that order. The rejection for an ungoverned tool was not in the first draft of the handler, which passed unknown tools through; writing the fixture made the gap visible. And the response handler's first draft rewrote only structuredContent, until a test compared it with the text content and they differed.

10. Running it

From the repository root, every iteration's tests run in one command, and every test and proof together in another:

uv run pytest -v
./check.sh

The iteration also runs standalone:

uv run --project gateway pytest -v

11. Decisions made in this iteration

Gateway interceptors are the enforcement point. One Lambda per interception point, attached to the gateway, holding for every target. The Runtime API proxy extension is set aside.

The handlers add no governance. They parse, decode, name the verb, and call the wrappers already tested and proven. The test that the policies and entities are byte for byte the proven ones is the point.

An ungoverned tool is rejected. Every tool the gateway exposes must be in the table, the same completeness rule the contract build applies to columns.

The token is decoded, not re-verified. The Gateway's authorizer validates it before any interceptor runs. The handler reads the forwarded header only.

AgentCore Policy is a second check on the verb rules. It cannot see owners, tag maps, or responses; the interceptors can. Its policies would be generated from the corpus once the claim names are confirmed.

12. Open questions

  1. Deployment. The handlers are tested against documented events and not yet against a gateway. The first deployment will confirm the event shapes, the JSON-RPC error convention for a short-circuit, and whether the Gateway forwards the header the handler expects.
  2. Streaming responses. With streaming on, the response interceptor is invoked once per JSON-RPC event and only the first may change the status and headers. The row round works per event; the field round does too. Whether the upstream tools stream is a registration question.
  3. Payload size. A Lambda invocation carries at most 6 MB in and out. A large list response needs either the mask cache from iteration 1's review, so the field round costs one decision per distinct owner, or push-down of the row condition from iteration 9's open questions.
  4. The claims table from iteration 6, still assumed. The handlers read sub, act, and roles; the first deployment's token settles whether those are the names.
  5. Tool naming. The table keys follow the Gateway's target-and-operation convention with three underscores. The table itself could be generated from tool registration, which is the same act as contract publication in iteration 1's review.
  6. The agent's own identity, carried from iteration 6. Token exchange gives the exchanged token both the agent's and the caller's identity[7]; no rule reads the agent's yet.
